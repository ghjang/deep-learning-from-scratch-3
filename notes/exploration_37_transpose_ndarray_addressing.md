<a id="한장요약"></a>
## 0. 한 장 요약 — 관점 전환의 한 줄

> **다차원 배열은 메모리에 존재하지 않는다. 존재하는 건 1D 버퍼와 "해석 규칙(shape + strides)"뿐이다.**
> 전치는 데이터 이동이 아니라 **해석 규칙의 재배치** — 관찰자가 움직이는 것.

| 관점 (수술 전) | 관점 (수술 후) |
|---|---|
| 배열 = 종이 위의 격자 (데이터가 공간에 박힘) | 배열 = 1D 버퍼 + 어드레싱 규칙 (데이터는 한 줄) |
| 전치 = 종이를 접어 데이터를 옮김 | 전치 = **strides 순서 재배치** (버퍼 무동) |
| shape = 배열의 생김새 | shape = 총량(버퍼 크기) + 구조(strides 초기값)의 이중 역할 |
| 차원 = 물리적 공간 | 차원 = 인덱스의 이름표 (길이, 보폭) 묶음 |

<a id="기존세계관"></a>
## 1. 수술 전 상태 — 브로의 기존 세계관과 그 계보

브로의 원래 시각: **"2D 행렬을 종이에 그리고, 전치하면 종이의 내용을 대각선으로 접어 다시 그린다."**

이 세계관이 잘못된 게 아니다 — **선형대수의 세계에서는 완결**이었어:

- 행렬 = 선형 사상의 2D 표기 (수학 계보) — "종이"가 표준 모델
- C/C++ 시절: 3D+ 배열이 일반 코딩에 등장할 일이 없었음 (컴파일 타임 고정 shape)
- 2D 접기 그림은 **명세(수학)의 시각화**로서 교육적으로 유용 — 지금도 유용

문제는 세계가 확장된 것: 딥러닝이 (B, C, H, W) 같은 4D+를 일상으로 만들었고, 종이 그림 세계관으로는 상상이 막힘. **세계관 이사가 필요한 것뿐 — 브로의 머리가 굳은 게 아니라 시대가 이사한 것.** (탐구 노트 15 계보 감성: 종이 그림도 어원이 있는 하나의 발상이다)

<a id="일반정의"></a>
## 2. 전치의 일반 정의 — 2D 접기는 특수 케이스였다

- **정의**: 전치 = **축(axis) 순서의 재배치**. NumPy: `transpose(x, axes=(...))`
- 2D: `x.T` = `transpose(x, (1, 0))` — "대각선 접기"로 **보이지만** 본질은 축 순서 교환
- 3D: `(2, 3, 4)`에서 `transpose(1, 0, 2)` → `(3, 2, 4)` — **축 0과 1의 역할만 교환**
- ★ **1D는 no-op** (축이 하나라 교환할 짝이 없음) — "열↔행 벡터 전환"은 `(n,1)↔(1,n)`의 **2D 특수 케이스**이지 1D 전치가 아님. 1D를 진짜 행/열로 바꾸는 건 reshape 담당.
- 고차원 이미지: **"축의 역할 이름 바꾸기"** — 채널축↔공간축, head축↔seq축. 물리적 공간을 상상할 필요 없음 (점검표 10번에서 재확인)

<a id="메모리진실"></a>
## 3. 메모리의 진실 — 1D 버퍼 + shape + strides

NumPy ndarray의 내부 구조 (3요소):

```
[데이터 버퍼: 1차원 메모리 뭉치] + [shape: 축별 길이] + [strides: 축별 보폭(바이트)]
```

**stride = 보폭** (영어 뜻 그대로) — 어떤 축으로 인덱스를 1 늘릴 때 메모리에서 건너뛰는 바이트 수.

### 브로의 C 세계와의 재회

```c
int64_t buf[6] = {0, 1, 2, 3, 4, 5};
// 2D 접근: x[i][j] = buf[i*3 + j]      ← 브로가 하던 포인터 산술!
// 주소 공식: addr = base + i*24 + j*8   ← 이 계수가 곧 strides (24, 8)
```

- NumPy strides는 이 C 계수를 **축별로 들고 다니며 런타임에 재조립 가능하게 일반화**한 것
- ★ **shape의 이중 역할 분리** (수술의 핵심 중 하나):
  - **총량** (2×3=6) → 버퍼 크기에만 기여 — (2,3)이든 (3,2)든 (6,)이든 같은 48바이트
  - **구조** (2,3 순서) → strides 초기값에만 기여 (C순서 default)
  - 이 분리("버퍼=총량의 세계 / shape+strides=해석의 세계")가 view 전치의 비밀
- 단위 주의: NumPy는 **바이트**, PyTorch는 **원소 수** (`(2,3)` 텐서 stride가 `(3,1)`) — 두 세계의 함정

<a id="전치실체"></a>
## 4. 전치의 실체 — strides 재배치 (view)

transpose가 하는 일은 **strides 튜플의 순서만 재배치**:

```python
x     # shape (2, 3), strides (24, 8)
x.T   # shape (3, 2), strides (8, 24)   ← 버퍼 무동!
x.T.base is x   # True — view (복사 아님)
# 1000×1000 전치도 ~3e-07초 — O(1) (데이터 크기 무관)
```

### ★ "축을 바꾸면 원소 수가 변동?" → 아니 — (길이, 보폭) 묶음의 자리 이동

```
x   : 축0 = (길이 2, 보폭 24)   축1 = (길이 3, 보폭 8)
x.T : 축0 = (길이 3, 보폭 8)    축1 = (길이 2, 보폭 24)
      ↑ (길이 3, 보폭 8) 묶음이 통째로 축0으로 이사 — 내용물 그대로
```

- 총 원소·메모리 배치·최대 도달 오프셋 전부 불변: `(2,3)/(24,8)`나 `(3,2)/(8,24)`나 `1·24+2·8 = 2·8+1·24 = 40바이트`

### ★ "오프셋 보정을 누적 추적?" → 그런 시스템 자체가 없음

모든 원소 참조는 매번 **한 줄 공식**: `addr = base + Σ(인덱스 × 보폭)`.

`addr(i, j)`와 `addr'(j, i)`가 같은 주소가 되는 건 **곱셈 교환법칙** — 같은 두 항의 합에 인덱스 이름만 교환된 것. "보정"이 아니라 **공식의 대칭성**.

### 구체 예시 (숫자로 못박기)

```
버퍼 오프셋:  10@0  20@8  30@16  40@24  50@32  60@40

x[1,2]   = 1×24 + 2×8 = 40 → 60
x.T[2,1] = 2×8  + 1×24 = 40 → 60   ← 값도 주소도 같은 칸
```

- ★ **축이 주소를 소유하는 게 아니다** — (인덱스 조합 → 주소) 매핑이 strides로 정의될 뿐. 전치는 그 정의식의 계수 순서를 바꾸는 것. 유지되는 건 버퍼의 값뿐이고 그건 애초에 무동.
- 역방향 증명: transpose를 "종이 그림처럼" C연속 배열로 실제 받으려면 **copy 필요** — `ravel` 순서가 달라 보이는 이유 (`x.T.ravel()`은 C순서 재해석이라 다르게 읽힘)

<a id="관찰자비유"></a>
## 5. 관찰자 비유 — 종이는 그대로, 내가 움직인다

> 브로: *"종이인쇄된 2D 행렬을 종이 자체는 그대로 두고, 그 주위를 내가 움직여서 다른 식으로 보는 것?"*

정확한 비유. **관찰자 위치 = 어드레싱 규칙.** 전치는 종이(버퍼)를 조작하는 게 아니라 관찰자(규칙)가 자리를 옮기는 것. 종이 그림 교육은 "종이를 다시 그리는" 관점이었고, stride 세계는 "관찰자가 걸어다니는" 관점.

<a id="두파벨"></a>
## 6. 배치 순서의 두 파벨 — row-major vs column-major

같은 (2,3) 배열도 버퍼에 깔리는 순서가 두 파벨:

| 파벨 | 첫 인덱스의 보폭 | 채택 |
|---|---|---|
| **row-major (C 순서)** | 최대 — 나머지 영역 전체 점프 (`[i][j]`의 i가 행, 행 전체를 뛰어넘음) | C, C++, **NumPy 기본** (`order='C'`) |
| **column-major (F 순서)** | 최소 — 다음 원소 (Fortran `A(i,j)`의 i가 열) | Fortran, MATLAB, R |

- C++ 다차원 배열 문법은 **신택틱 슈거**: `a[i][j]` → `*(base + i*3 + j)` (컴파일러가 계수 계산) — shape 컴파일 타임 고정이라 재조립 발상이 필요 없었던 세계
- ★ 재미 연결: **C순서 행렬을 전치된 어드레싱으로 보는 것 ≈ F순서로 보는 것** — 전치와 배치 순서가 만나는 지점. `np.ascontiguousarray(x.T)`는 copy를 동반하는 이유도 여기 (C순서로 다시 깔아야 하니까)

<a id="이중성"></a>
## 7. 두 세계의 이중성 — 수학엔 메모리가 없다

> 브로: *"수학적 다차원은 메모리 개념이 없는데, 물리 메모리 지식이 혼란을 유발"*

정확한 자기 진단. 이 이중성은 이 프로젝트의 반복 테마:

| 세계 | 다차원의 모습 | 전치의 의미 |
|---|---|---|
| **수학** ($\mathbb{R}^n$) | 좌표 추상 — 순서 없음, 메모리 없음 | 관계(재배치)만 존재 |
| **구현** (메모리) | 1D 버퍼 + 어드레싱 — **배치 순서 필연** | strides 재배치 (view) |

- 수학엔 "누가 먼저 저장됐나"라는 질문 자체가 없음. 구현은 버퍼가 1D라 순서가 강제로 생김.
- 두 세계를 오가는 **번역 규칙이 shape/strides** — 혼란은 국경에서 발생 (브로가 겪은 것)
- 같은 이중성의 발현: 노트 34 §5 (명세 vs 실행 — VJP와 전치 둘 다), 노트 35 §9 (구현 텐서 vs 수학 텐서). **세 번째 만남이 여기.**

<a id="실전지도"></a>
## 8. 실전 지도 — 3D+ 전치가 매일 일어나는 곳

| 사례 | 전치 | 차원 |
|---|---|---|
| PyTorch(CHW) ↔ TF/NumPy(HWC) 이미지 변환 | `(H, W, C) ↔ (C, H, W)` | 3D |
| 배치 이미지 | `(B, C, H, W)` 정렬/재배치 | 4D |
| Transformer 어텐션 | `(B, S, H, D) → (B, H, S, D)` — head 축 앞으로 | 4D |
| CNN (5고지) | 합성곱 축 정렬, im2col 전후 | 4D+ |

- 밑시딥3 타임라인: **reshape/transpose = step38, sum = step39, broadcast_to/sum_to = step40, matmul = step41** — 4고지가 이 순서로 "구조 연산도 미분 가능"을 펼침 (노트 35 §4와 1:1)

<a id="역전파연결"></a>
## 9. 역전파와의 연결 — 뷰 규칙의 왕복

- transpose의 VJP = **역 transpose** (gradient에 같은 축 교환을 다시 적용)
- stride 관점: forward에서 바꾼 strides 순서를 backward에서 되돌리는 것 — **데이터가 아니라 뷰 규칙을 왕복**
- reshape도 마찬가지 (역 reshape). 구조 연산의 역전파가 전부 "역 재배치"인 이유 — 명세(재배치된 행렬)와 실행(stride view)이 다르지만 backward는 실행 규칙을 그대로 뒤집으면 되는 것
- 이것도 "야코비안(치환행렬)을 만들지 않는다" (노트 34)의 한 사례
