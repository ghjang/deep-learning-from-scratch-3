## 0. 한 장 요약 — 관점 전환의 한 줄

> **다차원 배열은 메모리에 존재하지 않는다. 존재하는 건 1D 버퍼와 "해석 규칙(shape + strides)"뿐이다.**
> 전치는 데이터 이동이 아니라 **해석 규칙의 재배치** — 관찰자가 움직이는 것.

| 관점 (수술 전) | 관점 (수술 후) |
|---|---|
| 배열 = 종이 위의 격자 (데이터가 공간에 박힘) | 배열 = 1D 버퍼 + 어드레싱 규칙 (데이터는 한 줄) |
| 전치 = 종이를 접어 데이터를 옮김 | 전치 = **strides 순서 재배치** (버퍼 무동) |
| shape = 배열의 생김새 | shape = 총량(버퍼 크기) + 구조(strides 초기값)의 이중 역할 |
| 차원 = 물리적 공간 | 차원 = 인덱스의 이름표 (길이, 보폭) 묶음 |
| 수학의 전치 = 종이 접기 (2D 시각화) | 수학의 전치 = **내적 보존**(쌍대 사상) — 그림 없이 차원 무관 |

## 1. 수술 전 상태 — 브로의 기존 세계관과 그 계보

브로의 원래 시각: **"2D 행렬을 종이에 그리고, 전치하면 종이의 내용을 대각선으로 접어 다시 그린다."**

이 세계관이 잘못된 게 아니다 — **선형대수의 세계에서는 완결**이었어:

- 행렬 = 선형 사상의 2D 표기 (수학 계보) — "종이"가 표준 모델
- C/C++ 시절: 3D+ 배열이 일반 코딩에 등장할 일이 없었음 (컴파일 타임 고정 shape)
- 2D 접기 그림은 **명세(수학)의 시각화**로서 교육적으로 유용 — 지금도 유용

문제는 세계가 확장된 것: 딥러닝이 (B, C, H, W) 같은 4D+를 일상으로 만들었고, 종이 그림 세계관으로는 상상이 막힘. **세계관 이사가 필요한 것뿐 — 브로의 머리가 굳은 게 아니라 시대가 이사한 것.** (탐구 노트 15 계보 감성: 종이 그림도 어원이 있는 하나의 발상이다)

**★ 정밀 진단 보정 (2026-08-28, 브로 정독 중 자기 진단)**: 위 진단("4D+에서 상상이 막힘")보다 벽은 한 칸 앞이었다 — **3D부터**. 2D 전치는 "대각선 접기" 그림으로 시각 트릭이 먹는 마지막 차원이라, 일반 정의 없이도 동작을 예측할 수 있었다. 3D에서 "큐브를 접는" 상상이 성립하지 않는 순간이 곧 일반 정의(축 재배치) 부재가 드러난 지점. 즉 "4D를 이해 못 한다"가 아니라 "3D에서 이미 일반 정의를 몰랐다 — 2D 그림 트릭이 가려줬을 뿐"이 정확한 수술 전 상태.

### ★★ 이 현상에게 이름이 있다 — concept image vs concept definition (2026-08-28 대화)

> 브로: *"삼각함수 하면 삼각형만 떠올라서 '반복·주기' 표현이라는 생각을 못 하는 것 같은 느낌. 이 전치 쪽이 더 심한 느낌."*

수학교육학의 정식 용어 — **concept image vs concept definition** (Tall & Vinner, 1981):

- **concept image**: 개념과 함께 자동으로 떠오르는 머릿속 표상 (그림, 절차, 대표 예시)
- **concept definition**: 공식 정의 — 성질과 관계로 된 것

머릿그림이 정의를 잠식하면, 정의가 확장돼도 그림 안에서만 생각하게 됨. 삼각형 이미지가 "sin = 주기함수"를 가리는 것과, 종이 접기 이미지가 "전치 = 축 재배치"를 가리는 것은 **같은 병**.

- ★ **전치 쪽이 더 악성인 이유**: 삼각형 그림은 각이 90도 넘어가자마자 금이 가서 일찍 포기하게 해주지만, 2D 접기는 **2D 안에서는 완전히 성공하는 알고리즘**이라 스스로를 정의로 위장함. 차원이 늘어나는 순간에만 들통.
- ★ 브로의 일반화 (이 대화의 산물): **"저차원을 설명하기에 충분했던 것이, 차원을 올려 의미를 확장하는 순간 방해물이 된다."** — 수학자들이 그림 대신 성질로 정의를 쓰는 이유의 한 문장 요약. 성질로 정의하면 차원이 늘어나도 자동으로 확장됨.
- 같은 병의 예고 환자: **미분 = "접선의 기울기" 이미지** — 1차원에선 완벽하지만 다변수로 올라가면 그림이 없어 막힘. 고급 정의는 "미분 = 선형 근사" (§9의 4고지 예고에서 회수).

## 2. 축의 기초와 전치의 일반 정의 — 2D 접기는 특수 케이스였다

### 예비 2.0 — 축(axis)이란 무엇인가 (브로 요청, 2026-08-28)

전치가 "축의 재배치"라면 축부터 정의해야 한다 — 이 노트에 빠져 있던 기초.

**정의**: 축 = **인덱스가 움직이는 방향 하나하나**. shape이 (2, 3, 4)면 축이 3개 — 축0(길이 2), 축1(길이 3), 축2(길이 4). 원소 하나를 지정하려면 각 축에서 인덱스를 하나씩 골라 조합: `a[i, j, k]`.

**아파트 비유** (한 번 잡으면 고차원에도 유효):

```
shape (2, 3, 4) = 2층 건물 × 층마다 3개 호 × 호마다 4개 방
a[1, 2, 0] = "1층 2호 0번 방" — 인덱스 (i,j,k)는 방의 주소
축0 = 층 번호가 움직이는 방향
축1 = 호 번호가 움직이는 방향
축2 = 방 번호가 움직이는 방향
```

**"행렬의 축" (2D에서의 대응)**:

| 축 | 2D 이름 | 방향 | 연산 관례 |
|---|---|---|---|
| 축0 | 행 방향 (row) | **세로로 내려가는** 인덱스 | `np.sum(a, axis=0)` = 행을 따라 내려가며 합 = **각 열의 합** (결과에서 축0이 접힘/제거됨) |
| 축1 | 열 방향 (column) | 가로로 이동하는 인덱스 | `np.sum(a, axis=1)` = 각 행의 합 |

- ★ 연산의 축 해석: `axis=n` = "축 n을 **따라가며** 연산해 그 축을 **접는다(제거)**" — 결과 shape에서 그 축이 사라짐
- 축 번호 관례: 0부터 시작, **-1 = 마지막 축** (`axis=-1`은 자주 씀 — 4고지에서)
- 축 수 = `ndim` — "3차원 배열" = 축이 3개 (물리적 3차원 공간과 무관!)

**피벗(pivot)** — 브로가 들어본 단어의 정체: 엑셀/데이터프레임의 **피벗 테이블**은 "어느 축을 행에 놓고 어느 축을 열에 놓을지 재배치하는 것" — 즉 **축 재배치 개념의 데이터 분석 버전** (같은 계보). NumPy의 근친: `np.moveaxis(x, src, dst)` (축 하나 이동), `np.swapaxes(x, a, b)` (둘 교환) — transpose의 부분 연산들.

이제 "전치 = 축 순서의 재배치"가 읽힌다 — **아파트에서 층/호/방의 이름표를 서로 바꾸는 것** (방은 그대로, 주소 체계만 교체).

### 2.1 전치의 정의

- **정의**: 전치 = **축(axis) 순서의 재배치**. NumPy: `transpose(x, axes=(...))`
- 2D: `x.T` = `transpose(x, (1, 0))` — "대각선 접기"로 **보이지만** 본질은 축 순서 교환
- 3D: `(2, 3, 4)`에서 `transpose(1, 0, 2)` → `(3, 2, 4)` — **축 0과 1의 역할만 교환**
- ★ **1D는 no-op** (축이 하나라 교환할 짝이 없음) — "열↔행 벡터 전환"은 `(n,1)↔(1,n)`의 **2D 특수 케이스**이지 1D 전치가 아님. 1D를 진짜 행/열로 바꾸는 건 reshape 담당.
- 고차원 이미지: **"축의 역할 이름 바꾸기"** — 채널축↔공간축, head축↔seq축. 물리적 공간을 상상할 필요 없음 (점검표에서 재확인)

### ★ 3D 양끝 축 맞바꾸기 — transpose(2, 1, 0) (2026-08-28 브로 검증 문항)

> 브로: *"3차원에서 1번째 축과 3번째 축을 바꾼다면? 메모리는 가만히 있는데, 전치 후 주소는?"*

shape (2, 3, 4)에서 축0과 축2를 맞바꾸기 = `transpose(2, 1, 0)`:

- **shape**: (2, 3, 4) → (4, 3, 2) — 양끝만 맞바꿈, **가운데 축1은 구경꾼**
- **주소 대응 규칙**: `a[i, j, k] == b[k, j, i]` — 좌표는 축이 이사 간 자리를 따라감 (i와 k 맞바꿈, j 제자리)
- 아파트로: "1층 2호 0번 방"이 새 주소체계에서는 "0층 2호 1번 방" — 방은 못 갔고 주소만 재발급
- (이 대응이 정말 같은 칸을 찾아내는지의 숫자 검증은 §4로 미룸 — strides를 아직 안 배웠으니 여기선 좌표 규칙만)
- 3D는 축 순서 배치가 3! = 6가지 전부 있는데 `transpose(axes=...)`로 전부 표현 가능 — 축0·축2 맞바꾸기는 `np.swapaxes(x, 0, 2)` 한 방으로도 됨 (§2.0의 moveaxis/swapaxes)
- ★ 2D의 `a[i,j] == b[j,i]`와 **구조 완전 동일** — 좌표가 하나 더 늘었을 뿐. 차원 수는 규칙의 난이도를 바꾸지 않음 (그림의 난이도만 바꿈)

## 3. 메모리의 진실 — 1D 버퍼 + shape + strides

NumPy ndarray의 내부 구조 (3요소):

```
[데이터 버퍼: 1차원 메모리 뭉치] + [shape: 축별 길이] + [strides: 축별 보폭(바이트)]
```

**stride = 보폭** (영어 뜻 그대로) — 어떤 축으로 인덱스를 1 늘릴 때 메모리에서 건너뛰는 바이트 수.

### 브로의 C 세계와의 재회

```c
int64_t buf[6] = {0, 1, 2, 3, 4, 5};
// 2D 접근: x[i][j] = buf[i*3 + j]      ← 브로가 하던 포인터 산술!
// 주소 공식: addr = base + i*24 + j*8   ← 이 계수가 곧 strides (24, 8)
```

- NumPy strides는 이 C 계수를 **축별로 들고 다니며 런타임에 재조립 가능하게 일반화**한 것
- ★ **shape의 이중 역할 분리** (수술의 핵심 중 하나):
  - **총량** (2×3=6) → 버퍼 크기에만 기여 — (2,3)이든 (3,2)든 (6,)이든 같은 48바이트
  - **구조** (2,3 순서) → strides 초기값에만 기여 (C순서 default)
  - 이 분리("버퍼=총량의 세계 / shape+strides=해석의 세계")가 view 전치의 비밀
- 단위 주의: NumPy는 **바이트**, PyTorch는 **원소 수** (`(2,3)` 텐서 stride가 `(3,1)`) — 두 세계의 함정

### ★ C++ 표현 3가지와의 매핑 — 브로 혼란의 숨은 원인 (2026-08-28 질문에서)

> 브로: *"C++에 정적 배열, 래그드 어레이, 1D 버퍼+포인터 계산 등 여러 방식이 있는데 그게 다차원 전치 이야기와 섞여 완전히 헷갈렸다."*

| C++ 방식 | 메모리 | stride 모델 |
|---|---|---|
| 정적 배열 `int a[2][3][4]` | 연속 — strides 컴파일타임 고정 | O (NumPy의 조상, 단 재조립 불가) |
| **래그드 배열** (`int**`, 행별 할당) | **비연속!** 행마다 별도 버퍼, 크기 들쭉날쭉 가능 | ✗ **적용 불가** — NumPy ndarray는 ragged가 아님 |
| 1D 버퍼 + 수동 계산 `buf[i*N+j]` | 연속 | O — strides를 손으로 계산하는 것 |

★ 래그드 배열은 "다차원"처럼 보이지만 stride 모델이 통하지 않는 **완전히 다른 구조** — 세 가지가 한 서랍에 있으면 혼란. NumPy ndarray는 언제나 **연속 버퍼(또는 그 view)**.

### ★ "첫 차원이 가장 큰 차원?" — 길이와 보폭의 분리

`a[2][3][4]`의 첫 축: **길이는 2 (가장 작음!), 보폭은 최대** (한 걸음에 나머지 3×4=12칸 점프). "큰 차원"의 뜻을 길이로 잡으면 첫 축은 최소, 보폭으로 잡으면 최대 — 이 둘이 섞이면 혼란의 씨앗.

### ★ strides의 정체 — 혼합 진법(mixed-radix) 수 표기 (2026-08-28 대화)

오프셋 공식 `i×s₀ + j×s₁ + k×s₂`는 사실 **(i, j, k)를 세 자릿수로 하는 혼합 진법 숫자 계산** — 자리마다 밑이 다른 진법 (십진법의 일반화):

- (2, 3, 4) 배열의 row-major: s₂ = 1, s₁ = 4, s₀ = 12 — "일의 자리는 4바닥, 십의 자리는 3바닥, 백의 자리는 2바닥"인 숫자
- **일상의 혼합 진법 = 시계**: (시, 분, 초) = (24, 60, 60)바닥 세 자릿수. "1일 3시간 25분"을 초로 환산하는 `1×86400 + 3×3600 + 25×60`이 곧 strides 곱셈 (1일 = 86400초가 stride)
- ★ 즉 "인덱스 튜플을 한 줄(1차원)로 펴는 규칙"은 컴퓨터가 없어도 인류가 써온 기술 — 단, 수학 세계에서는 개념의 일부가 아니라 **선택사항** (§7의 생존표와 칸토어 대각선 참조)

<a id="전치실체"></a>
## 4. 전치의 실체 — strides 재배치 (view)

transpose가 하는 일은 **strides 튜플의 순서만 재배치**:

```python
x     # shape (2, 3), strides (24, 8)
x.T   # shape (3, 2), strides (8, 24)   ← 버퍼 무동!
x.T.base is x   # True — view (복사 아님)
# 1000×1000 전치도 ~3e-07초 — O(1) (데이터 크기 무관)
```

### ★ view의 3요소와 자기 검증 (2026-08-28 대화)

> 브로: *"transpose가 리턴하는 뷰는, 전치된 strides 정보가 들어가 있다는 상황이군?"*

정확 — transpose가 반환하는 view는 **"새 명찰(배열 객체) 하나 + 같은 버퍼"**. 명찰에 적힌 것:

- **shape**: 전치된 shape
- **strides**: 전치된 strides
- **버퍼 포인터**: 동일 (복사 0바이트)

```python
import numpy as np

a = np.arange(24).reshape(2, 3, 4)
b = a.transpose(2, 1, 0)

b.strides       # (8, 32, 96)  ← 전치된 strides (바이트 단위; 칸 수 (1, 4, 12) × 8바이트)
b.shape         # (4, 3, 2)
b.base is a     # True — 같은 버퍼 공유
b[0, 0, 0] = 999
a[0, 0, 0]      # 999 — b를 고쉬면 a도 변함 (몸통이 하나라는 증거)
```

- 마지막 두 줄이 view의 서약 — 값을 통한 수정이 원본에 반영됨. 데이터 복사가 없으니 당연
- strides가 칸 수가 아니라 **바이트 수**라는 점 재확인 (§3의 단위 주의 — int64라 칸당 8바이트)

### ★ "축을 바꾸면 원소 수가 변동?" → 아니 — (길이, 보폭) 묶음의 자리 이동

```
x   : 축0 = (길이 2, 보폭 24)   축1 = (길이 3, 보폭 8)
x.T : 축0 = (길이 3, 보폭 8)    축1 = (길이 2, 보폭 24)
      ↑ (길이 3, 보폭 8) 묶음이 통째로 축0으로 이사 — 내용물 그대로
```

- 총 원소·메모리 배치·최대 도달 오프셋 전부 불변: `(2,3)/(24,8)`나 `(3,2)/(8,24)`나 `1·24+2·8 = 2·8+1·24 = 40바이트`

### ★ "오프셋 보정을 누적 추적?" → 그런 시스템 자체가 없음

모든 원소 참조는 매번 **한 줄 공식**: `addr = base + Σ(인덱스 × 보폭)`.

`addr(i, j)`와 `addr'(j, i)`가 같은 주소가 되는 건 **곱셈 교환법칙** — 같은 두 항의 합에 인덱스 이름만 교환된 것. "보정"이 아니라 **공식의 대칭성**.

### 구체 예시 (숫자로 못박기)

```
버퍼 오프셋:  10@0  20@8  30@16  40@24  50@32  60@40

x[1,2]   = 1×24 + 2×8 = 40 → 60
x.T[2,1] = 2×8  + 1×24 = 40 → 60   ← 값도 주소도 같은 칸
```

3D 에코 — §2.1에서 미뤄둔 숫자 검증 (`transpose(2, 1, 0)`, 단위: 칸):

```
a        # shape (2, 3, 4), strides (12, 4, 1)
b        # shape (4, 3, 2), strides (1, 4, 12)   ← 양끝만 맞바꿈, 가운데 보폭 4는 제자리

a[1,2,0] = 1×12 + 2×4 + 0×1 = 20번 칸
b[0,2,1] = 0×1  + 2×4 + 1×12 = 20번 칸   ← §2.1의 주소 대응 a[i,j,k] == b[k,j,i] 검증 완료
```

- ★ 2D 예시와 **구조 완전 동일** — 좌표와 계수가 하나씩 늘었을 뿐. 차원 수는 규칙의 난이도를 바꾸지 않음

- ★ **축이 주소를 소유하는 게 아니다** — (인덱스 조합 → 주소) 매핑이 strides로 정의될 뿐. 전치는 그 정의식의 계수 순서를 바꾸는 것. 유지되는 건 버퍼의 값뿐이고 그건 애초에 무동.
- 역방향 증명: transpose를 "종이 그림처럼" C연속 배열로 실제 받으려면 **copy 필요** — `ravel` 순서가 달라 보이는 이유 (`x.T.ravel()`은 C순서 재해석이라 다르게 읽힘)

### ★★ "선언의 차원 순서 바꾸기" ≠ 전치 (핵심 교정, 2026-08-28 브로 질문에서)

> 브로: *"`int arr[2][3][4]`을 `int arr[4][3][2]`로 바꾸는 건 전치가 아니잖아? 이게 내 혼란 포인트와 섞여 있을지도."*

**정확한 지적 — 이건 전치가 아니라 별개의 새 배열이다:**

```
a = int[2][3][4]           strides (48, 16, 4)   ← C순서 계산
a.transpose(2,0,1)         shape (4,2,3), strides (4, 48, 16)  ← 같은 버퍼 재배치 ★전치★
b = int[4][3][2]           strides (24, 8, 4)    ← 다른 버퍼, 새로 C순서 계산 ★별개 배열★
```

- b는 shape 숫자 나열이 우연히 반대 **순서일 뿐** — strides 구성이 전혀 다름
- **전치 = 같은 버퍼 + strides 재배치 / 선언 변경 = 다른 버퍼 + 새 strides**
- ★ 브로 혼란의 뿌리: "차원 크기 나열 바꾸기"(선언)와 "축 순서 재배치"(전치)가 머릿속 같은 서랍에 있었던 것 — NumPy에서 shape을 바꾸는 연산은 reshape(버퍼 재해석, 조건부 view)이지 전치가 아님.

<a id="관찰자비유"></a>
## 5. 관찰자 비유 — 종이는 그대로, 내가 움직인다

> 브로: *"종이인쇄된 2D 행렬을 종이 자체는 그대로 두고, 그 주위를 내가 움직여서 다른 식으로 보는 것?"*

정확한 비유. **관찰자 위치 = 어드레싱 규칙.** 전치는 종이(버퍼)를 조작하는 게 아니라 관찰자(규칙)가 자리를 옮기는 것. 종이 그림 교육은 "종이를 다시 그리는" 관점이었고, stride 세계는 "관찰자가 걸어다니는" 관점.

### ★ 브로의 관점 전환 순간 — 실측 기록 (2026-08-28)

> 브로: *"자꾸 머리에서 뭘 그리려 하는데, 걍 1차원 겁나 긴 놈이라 생각하면... 1차원 상의 특정 위치에 똬~악 매칭되는구만?"*

```
머리가 하려던 것: 3D 큐브를 머릿속에서 돌리고 접고      ← 이걸 포기하는 순간
실체:            [0][1][2][3]...[23] 겁나 긴 한 줄     ← 배열의 진짜 몸통
부속품:          (shape, strides) 얇은 안내서           ← 인덱스 읽는 법
전치:            안내서 숫자 몇 개 맞바꾸기              ← 끝. 몸통 무변동
```

인덱싱의 실체도 동일 — `a[i,j,k]`를 받은 NumPy는 strides 안내서대로 `i×s₀ + j×s₁ + k×s₂`를 계산해 그 한 칸을 읽을 뿐. "그림을 그리려다 포기하고 규칙으로 전환"한 이 순간이 이 노트 전체의 목적지 — §1의 concept image 문제와 §7의 이중성이 만나는 지점.

<a id="두파벨"></a>
## 6. 배치 순서의 두 파벨 — row-major vs column-major

같은 (2,3) 배열도 버퍼에 깔리는 순서가 두 파벨:

| 파벨 | 첫 인덱스의 보폭 | 채택 |
|---|---|---|
| **row-major (C 순서)** | 최대 — 나머지 영역 전체 점프 (`[i][j]`의 i가 행, 행 전체를 뛰어넘음) | C, C++, **NumPy 기본** (`order='C'`) |
| **column-major (F 순서)** | 최소 — 다음 원소 (Fortran `A(i,j)`의 i가 열) | Fortran, MATLAB, R |

- C++ 다차원 배열 문법은 **신택틱 슈거**: `a[i][j]` → `*(base + i*3 + j)` (컴파일러가 계수 계산) — shape 컴파일 타임 고정이라 재조립 발상이 필요 없었던 세계
- ★ 재미 연결: **C순서 행렬을 전치된 어드레싱으로 보는 것 ≈ F순서로 보는 것** — 전치와 배치 순서가 만나는 지점. `np.ascontiguousarray(x.T)`는 copy를 동반하는 이유도 여기 (C순서로 다시 깔아야 하니까)
- 어원 보석 (2026-08-28 브로 질문): "파벨"은 **파벌(派閥)**의 커뮤니티식 표기 — 벌(閥)은 재벌(財閥)·문벌의 그 벌. "큰 집단 안에서 끼리끼리 모이는 패거리"라는 뜻으로, 두 배치 순서 진영이 각자의 기본값을 사수하며 수십 년째 대립하는 뉘앙스를 노리고 채택한 표기

<a id="이중성"></a>
## 7. 두 세계의 이중성 — 수학엔 메모리가 없다

> 브로: *"수학적 다차원은 메모리 개념이 없는데, 물리 메모리 지식이 혼란을 유발"*

정확한 자기 진단. 이 이중성은 이 프로젝트의 반복 테마:

| 세계 | 다차원의 모습 | 전치의 의미 |
|---|---|---|
| **수학** ($\mathbb{R}^n$) | 좌표 추상 — 순서 없음, 메모리 없음 | 관계(재배치)만 존재 |
| **구현** (메모리) | 1D 버퍼 + 어드레싱 — **배치 순서 필연** | strides 재배치 (view) |

- 수학엔 "누가 먼저 저장됐나"라는 질문 자체가 없음. 구현은 버퍼가 1D라 순서가 강제로 생김.
- 두 세계를 오가는 **번역 규칙이 shape/strides** — 혼란은 국경에서 발생 (브로가 겪은 것)
- 같은 이중성의 발현: 노트 34 §5 (명세 vs 실행 — VJP와 전치 둘 다), 노트 35 §9 (구현 텐서 vs 수학 텐서). **세 번째 만남이 여기.**

### ★★ 수학자의 전치 — 그림이 아니라 구조로 정의된다 (2026-08-28 질문: "컴퓨터가 없었다면?")

> 브로: *"수학자들은 메모리를 생각조차 안 했을 것 아닌가. 그럼 어떻게 생각했을까? shape, 원소 수, 좌표, strides 같은 개념이 수학 세계에서도 유효한가?"*

수학자는 전치를 "접어서 다시 그리기"로 정의한 적이 없음 — **선형 사상의 언어**로 정의:

$$\langle A^T y,\, x \rangle = \langle y,\, Ax \rangle$$

- "입력·출력 자리를 바꿔 대입해도 내적이 보존되는 사상"으로 Aᵀ를 규정 (쌍대 사상/수반 사상이라 부름)
- 성분 버전 $(A^T)_{ij} = A_{ji}$는 이 구조의 **좌표 표현**일 뿐
- 고차원(텐서)도 동일 — 인덱스 순서 바꾸기 = 다중선형 사상의 **인수 자리 맞바꾸기**: $B(x_2, x_1, x_3) = A(x_1, x_2, x_3)$
- ★ 선형 사상(구조) vs 행렬(좌표 표현)의 관계가 전치에도 그대로 — "종이 접기"는 좌표 표현의 2D 시각화에 불과했던 것

### ★ 컴퓨터를 제거했을 때 — 개념 생존표 (브로 질문에 대한 직답)

| 개념 | 수학 세계에서 |
|---|---|
| shape | ✅ 생존 — "크기 n₁×n₂×n₃인 지표 순서쌍들의 집합" |
| 원소 수 | ✅ 생존 — 순수 조합론. 축 순열은 인덱스 집합 위의 전단사 |
| 좌표 | ✅ 생존 — 인덱스 (i, j, k)는 그냥 순서쌍 |
| **strides** | ❌ **소멸** — "순서쌍 집합을 1차원 한 줄로 펴는 규칙"이라 저장(메모리)이 등장해야만 필요해지는 개념 |

- 수학자도 줄세우기가 필요할 때는 했음 — 사전순 배열, **칸토어의 대각선 훍기** (ℕ×ℕ의 크기를 셀 때). 흥미롭게도 칸토어 대각선은 row-major와 **다른 선형화** — 둘 다 정당한 전단사
- ★ 즉 **선형화는 진리가 아니라 선택** — 구현 세계에서 그 선택이 strides라는 숫자로 강제될 뿐 (§3의 혼합 진법 참조)

<a id="실전지도"></a>
## 8. 실전 지도 — 3D+ 전치가 매일 일어나는 곳

> 표기: "3D+" = **3차원 이상 전부** — '+'는 "그 이상 전부" 뜻의 줄임 ("19+", "iOS 15+"와 같은 패턴).

| 사례 | 전치 | 차원 |
|---|---|---|
| PyTorch(CHW) ↔ TF/NumPy(HWC) 이미지 변환 | `(H, W, C) ↔ (C, H, W)` | 3D |
| 배치 이미지 | `(B, C, H, W)` 정렬/재배치 | 4D |
| Transformer 어텐션 | `(B, S, H, D) → (B, H, S, D)` — head 축 앞으로 | 4D |
| CNN (5고지) | 합성곱 축 정렬, im2col 전후 | 4D+ |

- 밑시딥3 타임라인: **reshape/transpose = step38, sum = step39, broadcast_to/sum_to = step40, matmul = step41** — 4고지가 이 순서로 "구조 연산도 미분 가능"을 펼침 (노트 35 §4와 1:1)

<a id="역전파연결"></a>
## 9. 역전파와의 연결 — 뷰 규칙의 왕복

- transpose의 VJP = **역 transpose** (gradient에 같은 축 교환을 다시 적용)
- stride 관점: forward에서 바꾼 strides 순서를 backward에서 되돌리는 것 — **데이터가 아니라 뷰 규칙을 왕복**
- reshape도 마찬가지 (역 reshape). 구조 연산의 역전파가 전부 "역 재배치"인 이유 — 명세(재배치된 행렬)와 실행(stride view)이 다르지만 backward는 실행 규칙을 그대로 뒤집으면 되는 것
- 이것도 "야코비안(치환행렬)을 만들지 않는다" (노트 34)의 한 사례

### ★★ (Ax)·y = x·(Aᵀy) — 성분 전개로 유도된다 (2026-08-28 브로 질문)

> 브로: *"이 표현은 좌측 식에서 우측 식으로 원래 자연스럽게 유도가 가능한 것이었어?"*

가능 — **성분 전개 → 덧셈 순서 교환 → 재묶음** 세 단계뿐:

$$
(Ax)\cdot y
= \sum_i \Big(\sum_j A_{ij} x_j\Big) y_i
= \sum_i \sum_j A_{ij}\, x_j\, y_i
= \sum_j x_j \Big(\sum_i A_{ij}\, y_i\Big)
= \sum_j x_j\, (A^T y)_j
= x \cdot (A^T y)
$$

- 핵심 한 걸음: 유한 합의 순서 교환 (ΣᵢΣⱼ → ΣⱼΣᵢ) — 곱셈 교환법칙만큼이나 "특별한 것 없음"
- 안쪽 합 $\sum_i A_{ij} y_i$가 정확히 $(A^T y)$의 j번째 성분 — 전치의 정의가 유도 중간에서 자동 출현
- ★ 방향성은 양방향: "성분 뒤집기로 Aᵀ 정의 → 내적 보존 증명"도 되고, 반대로 "내적 보존으로 Aᵀ 규정 → 성분 뒤집기 도출"도 됨 (§7 수학자 정의와 잇는 닭-달걀)
- 실용적 마법: **식을 계산하기 편한 쪽으로 옮겨 담을 수 있다** — 역전파에서 전치가 맨날 튀어나오는 이유. 4고지 MatMul backward의 `gy @ W.T`가 이 성질의 현현 (step41에서 회수)

### ★ 4고지 예고 — 미분 = 선형 근사, 그리고 전치와의 재회 (2026-08-28 대화)

> 브로: *"'미분 = 선형 근사(야코비안)' — 벡터함수의 도함수가 야코비안이라서? 벡터함수라 부른 함수의 도함수 표현을 제대로 본 적이 없다."*

정확하며 한 겹 더 정밀하게:

- **정의 (프레셰 미분)**: $f: \mathbb{R}^n \to \mathbb{R}^m$이 x에서 미분 가능 = 선형 사상 L이 존재해 $f(x+h) = f(x) + L(h) + o(\|h\|)$. **미분 = 그 선형 사상 L 자체**
- **야코비안** = L의 표준기저 행렬 표현 (m×n, $J_{ij} = \partial f_i / \partial x_j$) — "선형 근사 ≒ 야코비안"은 사상과 행렬을 좌표계 안에서 동일시하는 편한 말
- 예: $f(x, y) = (xy,\, x+y)$ → $J = \begin{pmatrix} y & x \\ 1 & 1 \end{pmatrix}$
- 1차원(n=m=1): $L(h) = f'(x)\,h$ — **"접선의 기울기"는 선형 사상의 1×1 특수 케이스**. 그림이 없어져도 정의는 멀쩡 (§1 concept image 이야기의 회수 지점)
- ★ 사상(구조) vs 행렬(표현) 구분은 §7의 선형 사상 vs 행렬, 이 노트의 수학 vs 구현 이중성과 같은 패턴 — 노트 34 (야코비안은 흐르지 않는다)와 4고지 MatMul에서 세계가 합류
