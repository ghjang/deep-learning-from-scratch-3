## 0. 한 장 요약 — 관점 전환의 한 줄

> **다차원 배열은 메모리에 존재하지 않는다. 존재하는 건 1D 버퍼와 "해석 규칙(shape + strides)"뿐이다.**
> 전치는 데이터 이동이 아니라 **해석 규칙의 재배치** — 관찰자가 움직이는 것.

| 관점 (수술 전) | 관점 (수술 후) |
|---|---|
| 배열 = 종이 위의 격자 (데이터가 공간에 박힘) | 배열 = 1D 버퍼 + 어드레싱 규칙 (데이터는 한 줄) |
| 전치 = 종이를 접어 데이터를 옮김 | 전치 = **strides 순서 재배치** (버퍼 무동) |
| shape = 배열의 생김새 | shape = 총량(버퍼 크기) + 구조(strides 초기값)의 이중 역할 |
| 차원 = 물리적 공간 | 차원 = 인덱스의 이름표 (길이, 보폭) 묶음 |
| 수학의 전치 = 종이 접기 (2D 시각화) | 수학의 전치 = **내적 보존**(쌍대 사상) — 그림 없이 차원 무관 |

## 1. 수술 전 상태 — 브로의 기존 세계관과 그 계보

브로의 원래 시각: **"2D 행렬을 종이에 그리고, 전치하면 종이의 내용을 대각선으로 접어 다시 그린다."**

이 세계관이 잘못된 게 아니다 — **선형대수의 세계에서는 완결**이었어:

- 행렬 = 선형 사상의 2D 표기 (수학 계보) — "종이"가 표준 모델
- C/C++ 시절: 3D+ 배열이 일반 코딩에 등장할 일이 없었음 (컴파일 타임 고정 shape)
- 2D 접기 그림은 **명세(수학)의 시각화**로서 교육적으로 유용 — 지금도 유용

문제는 세계가 확장된 것: 딥러닝이 (B, C, H, W) 같은 4D+를 일상으로 만들었고, 종이 그림 세계관으로는 상상이 막힘. **세계관 이사가 필요한 것뿐 — 브로의 머리가 굳은 게 아니라 시대가 이사한 것.** (탐구 노트 15 계보 감성: 종이 그림도 어원이 있는 하나의 발상이다)

**★ 정밀 진단 보정 (2026-08-28, 브로 정독 중 자기 진단)**: 위 진단("4D+에서 상상이 막힘")보다 벽은 한 칸 앞이었다 — **3D부터**. 2D 전치는 "대각선 접기" 그림으로 시각 트릭이 먹는 마지막 차원이라, 일반 정의 없이도 동작을 예측할 수 있었다. 3D에서 "큐브를 접는" 상상이 성립하지 않는 순간이 곧 일반 정의(축 재배치) 부재가 드러난 지점. 즉 "4D를 이해 못 한다"가 아니라 "3D에서 이미 일반 정의를 몰랐다 — 2D 그림 트릭이 가려줬을 뿐"이 정확한 수술 전 상태.

### ★★ 이 현상에게 이름이 있다 — concept image vs concept definition (2026-08-28 대화)

> 브로: *"삼각함수 하면 삼각형만 떠올라서 '반복·주기' 표현이라는 생각을 못 하는 것 같은 느낌. 이 전치 쪽이 더 심한 느낌."*

수학교육학의 정식 용어 — **concept image vs concept definition** (Tall & Vinner, 1981):

- **concept image**: 개념과 함께 자동으로 떠오르는 머릿속 표상 (그림, 절차, 대표 예시)
- **concept definition**: 공식 정의 — 성질과 관계로 된 것

머릿그림이 정의를 잠식하면, 정의가 확장돼도 그림 안에서만 생각하게 됨. 삼각형 이미지가 "sin = 주기함수"를 가리는 것과, 종이 접기 이미지가 "전치 = 축 재배치"를 가리는 것은 **같은 병**.

- ★ **전치 쪽이 더 악성인 이유**: 삼각형 그림은 각이 90도 넘어가자마자 금이 가서 일찍 포기하게 해주지만, 2D 접기는 **2D 안에서는 완전히 성공하는 알고리즘**이라 스스로를 정의로 위장함. 차원이 늘어나는 순간에만 들통.
- ★ 브로의 일반화 (이 대화의 산물): **"저차원을 설명하기에 충분했던 것이, 차원을 올려 의미를 확장하는 순간 방해물이 된다."** — 수학자들이 그림 대신 성질로 정의를 쓰는 이유의 한 문장 요약. 성질로 정의하면 차원이 늘어나도 자동으로 확장됨.
- 같은 병의 예고 환자: **미분 = "접선의 기울기" 이미지** — 퇴화는 단계적 (2026-08-30 브로 질문 보강: *"2변수는 3D 그림 가능하지 않나?"* — 맞음): 1변수는 접선+기울기 숫자 완벽 → 2변수는 **접평면**까지 그림이 생존하나 "기울기 = 숫자 하나"가 소멸 (방향별 기울기 = 그래디언트 벡터로 승격) → 3변수+는 그래프 자체가 4D+라 시각화 사망. ★ 죽는 건 그림이 아니라 "기울기 = 스칼라" 개념 — 살아남는 접평면은 오히려 올바른 일반화(선형 근사의 그래프). 고급 정의는 "미분 = 선형 근사" (§9의 4고지 예고에서 회수).

## 2. 축의 기초와 전치의 일반 정의 — 2D 접기는 특수 케이스였다

### 예비 2.0 — 축(axis)이란 무엇인가 (브로 요청, 2026-08-28)

전치가 "축의 재배치"라면 축부터 정의해야 한다 — 이 노트에 빠져 있던 기초.

**정의**: 축 = **인덱스가 움직이는 방향 하나하나**. shape이 (2, 3, 4)면 축이 3개 — 축0(길이 2), 축1(길이 3), 축2(길이 4). 원소 하나를 지정하려면 각 축에서 인덱스를 하나씩 골라 조합: `a[i, j, k]`.

**아파트 비유** (한 번 잡으면 고차원에도 유효):

```
shape (2, 3, 4) = 2층 건물 × 층마다 3개 호 × 호마다 4개 방
a[1, 2, 0] = "1층 2호 0번 방" — 인덱스 (i,j,k)는 방의 주소
축0 = 층 번호가 움직이는 방향
축1 = 호 번호가 움직이는 방향
축2 = 방 번호가 움직이는 방향
```

**"행렬의 축" (2D에서의 대응)**:

| 축 | 2D 이름 | 방향 | 연산 관례 |
|---|---|---|---|
| 축0 | 행 방향 (row) | **세로로 내려가는** 인덱스 | `np.sum(a, axis=0)` = 행을 따라 내려가며 합 = **각 열의 합** (결과에서 축0이 접힘/제거됨) |
| 축1 | 열 방향 (column) | 가로로 이동하는 인덱스 | `np.sum(a, axis=1)` = 각 행의 합 |

- ★ 연산의 축 해석: `axis=n` = "축 n을 **따라가며** 연산해 그 축을 **접는다(제거)**" — 결과 shape에서 그 축이 사라짐
- 축 번호 관례: 0부터 시작, **-1 = 마지막 축** (`axis=-1`은 자주 씀 — 4고지에서)
- 축 수 = `ndim` — "3차원 배열" = 축이 3개 (물리적 3차원 공간과 무관!)

### ★★ axis 연산 국어 사전 — sum·contraction·해석 프로토콜 (2026-08-30 정독 중 브로 질문 세트)

**2D 예시**:

```python
a = np.array([[1, 2, 3],
              [4, 5, 6]])       # shape (2, 3) = 2행 × 3열

np.sum(a, axis=0)   # [5, 7, 9]  ← 1+4, 2+5, 3+6 — 각 열의 합, shape (3,)
np.sum(a, axis=1)   # [6, 15]    ← 1+2+3, 4+5+6 — 각 행의 합, shape (2,)
```

- **"행을 따라 내려간다"의 정확한 뜻**: 행 인덱스 i가 0→1로 변하는 동안 열 j는 고정 — 고정된 j의 값을 위아래로 모은다 → 열마다 하나의 값
  - ★ **항해 방향 ≠ 생존자**: axis=0을 따라 합하면 축0이 죽고 **열이 살아남는다** — "행 방향으로 간다"고 해서 결과가 행에 관한 것은 아님 (국어 함정)
  - 검증은 국어 대신 결과 shape: (2,3) --axis=0--> (3,)
  - 아파트 버전: (2층 × 3호)에서 axis=0 합 = 같은 호의 위아래 층 값을 합친다 → 호마다 하나 (3개)

- ★ **결과 [5, 7, 9]는 행이 아니다** (2026-08-30 브로 질문):
  - 1D 배열엔 행/열 구분 자체가 없음 (§2.1: 1D 전치 no-op와 같은 이유)
  - 가로로 보이는 건 print 관례일 뿐 — 진짜 행/열은 (1,3)/(3,1)로 reshape하는 순간부터
  - "보이는 것"과 "구조"의 혼동 — concept image 함정의 출력 버전 (§1)

- ★ **sum의 정체** (2026-08-30 브로 질문):
  - 문법(`np.sum`의 axis)은 NumPy 발명, 내용은 고전 수학 — 그 축 방향으로 **1-벡터와의 곱** (텐서 축소/contraction의 특수 케이스)
  - **축 수를 줄이는 건 해석 규칙 교체로는 불가능** (§3에서 배울 strides가 바꿀 수 있는 건 "읽는 법"뿐 — 축 수는 못 줄임)
  - 그래서 전치·reshape는 뷰(규칙 교체)지만 sum은 실제 계산으로 새 버퍼를 만든다 (노트 35 §4 구조 연산 vs 계산 연산 구분과 연결)

- ★ **행/열은 2D 시대의 유산 이름** (2026-08-30 브로 질문):
  - **축 번호가 일반 언어** — 3D+엔 축2 이상의 표준 이름이 없어 axis 번호 + 도메인 별명(batch/channel/head/...)을 씀
  - 2D조차 axis0/axis1으로 지칭해도 손해 없음 (PyTorch 오류 메시지도 "dim 0" 식)
  - 용어 함정: "행 방향"(= 축0, 행 인덱스가 움직임)과 "한 행"(= 축1 슬라이스)이 다른 뜻인데 말이 겹침

**3D 확장 — 성적표로 보는 contraction (2026-08-30 브로 질문)**:

```python
a = np.arange(24).reshape(2, 3, 4)
# 해석: (2학기, 3학생, 4과목) — 값은 그냥 0~23

a.sum(axis=0)   # shape (3, 4) — 학기 소멸: 각 학생×과목의 연간 합
a.sum(axis=1)   # shape (2, 4) — 학생 소멸: 각 학기×과목의 반 전체 합
a.sum(axis=2)   # shape (2, 3) — 과목 소멸: 각 학기×학생의 개인 총점

# 검증: a.sum(axis=0)[1, 2] = a[0,1,2] + a[1,1,2] = 6 + 18 = 24
```

- 규칙: **인덱스 n을 잊고, 나머지 자리가 같은 원소끼리 모두 더한 표** — 죽은 축이 무슨 역할이었는지(학기/학생/과목)가 결과의 해석을 결정 (축 = 역할 이름표)
- 어떤 축을 죽일지는 데이터 질문의 방향이 정한다: "연간 총점이 보고 싶다 → 학기를 죽여라 (axis=0)"
- ★ contraction은 sum만이 아님 (2026-08-30 브로 곱씹기): max·min·mean·prod 등 모든 **reduction**이 같은 트리 접기 — 형제 서브트리의 합병 연산이 +에서 max 등으로 바뀔 뿐. "요약 통계량을 만드는 차원 축소"라는 프레임이 정확 — 어떤 요약을 할지와 결과의 의미 해석은 응용 도메인이 정함

**★ 축 해석 프로토콜 3단계 — 국어 극복 주문 (2026-08-30 브로 요청)**:

1. **이름표부터** — shape를 쓰고 각 축에 역할 이름을 붙인다: `(2, 3, 4) = (학기, 학생, 과목)`
2. **질문을 축 언어로 번역** — "연간 총점 보고 싶다" → "학기 축을 죽인다" → `axis=0`
3. **결과 shape로 검증** — 죽인 축이 사라졌나? `(2,3,4) --axis=0--> (3,4)` ✓. 국어 직감은 재판에 부치지 않는다 — shape가 진실

- 보조 주문: `axis=n`을 볼 때마다 "n번 인덱스가 움직이는구나" 소리 내기 — **항해 방향**(움직이는 인덱스)과 **생존자**(결과에 남는 축)를 분리해서 듣는 훈련

- **피벗(pivot)** — 브로가 들어본 단어의 정체:
  - **피벗 테이블** (엑셀/데이터프레임): "어느 축을 행에 놓고 어느 축을 열에 놓을지 재배치하는 것" — **축 재배치 개념의 데이터 분석 버전** (같은 계보)
  - 어원 (2026-08-30 브로 질문): pivot = 원래 **회전축(축핀)** — 피벗 테이블/퀵정렬의 피벗/가우스 소거의 피벗 성분/스타트업의 사업 피벗 모두 "중심이 되어 다른 것이 돌아가는 기준"이라는 같은 어원의 확장
  - 단독 "피벗"은 문맥 없이는 못 정함 — 항상 수식어와 함께 등장 ("피벗팅"은 그 동사형)
  - NumPy의 근친: `np.moveaxis(x, src, dst)` (축 하나 이동), `np.swapaxes(x, a, b)` (둘 교환) — transpose의 부분 연산들
  - ★ 질문이 순열을 고른다 (2026-08-30 브로 발견): 외부인의 자연스러운 질문 *"채널별로 모아서 관찰할 수 있을까?"* 가 24개 조직화(S₄) 중 하나(CNHW)를 지정 — **질문 공간 ↔ 축 재배치의 대응**. 실무 질문은 대부분 "당기기 + reduction" 조합이고 풀순열 n!는 이론적 전체 공간. 산업 버전이 **OLAP**(슬라이스·다이스·피벗·롤업 — 데이터 웨어하우스의 질문 도구화)이며 엑셀 피벗 테이블이 그 UI. §5 관찰자 비유의 완성: **관찰자의 위치 = 관찰자의 질문**

### ★ 트리로 보는 다차원 배열 — 격자 이미지의 대체재 (2026-08-30 브로 아이디어)

> 브로: *"격자·표준공간 이미지 대신 트리로 생각하면? 루트에 축0 라벨, 직속 자식이 축0 슬라이스들, 그 아래로 나머지 축의 조합이 뻗어나가는 형태. 재미난 점 — 한 레벨 아래의 shape은 전부 같지 않나? 그리고 sum(axis=0)은 그 레벨을 순회하며 동일 shape 서브트리들을 전부 합치면 같은 shape 하나만 남는 것?"*

**재귀 정의** (브로 상상의 정식 버전): shape (2, 3, 4) = "2개짜리 배열, 각 원소는 (3,4) 배열, 그 각 원소는 (4,) 배열, 그 원소는 스칼라"

```
root (축0, fanout 2)
├─ a[0] ─ (3,4) 서브트리
│   ├─ a[0,0] ─ (4,) 서브트리 (잎 4개)
│   ├─ a[0,1] ─ ...
│   └─ a[0,2] ─ ...
└─ a[1] ─ (3,4) 서브트리   ← a[0]와 완전 동일 구조 (동질성)
```

- ★ **"한 레벨 아래 shape 전부 같다" = ndarray의 정의 조건** (균일 트리). 이 동질성이 깨지면 래그드 (§3의 그 매핑) — Python 중첩 리스트는 깨질 수 있어서 `np.array([[1,2],[3]])`가 말썽
- ★ **contraction의 트리 서술**: `sum(axis=k)` = 같은 부모를 둔 **형제 서브트리들을 동질성 덕에 원소별 합병** — 레벨 하나가 접힘. axis=0이면 루트 레벨 접힘 → (3,4) 하나만 남음 (브로 서술 그대로 정답)
- ★ **규칙은 층에 무관하게 일반화** (2026-08-30 브로 후속 질문): 접히는 층만 다르고 규칙(동질 형제의 원소별 합병)은 동일 — 위 axis=0 그림과 아래 axis=1·axis=2 그림을 대조:
  - **sum(axis=1)** — 1번 층(학생) 접힘:

    ```
    root (축0, 학기)
    ├─ a[0] ── 자식 3개: (4,), (4,), (4,) (동질) ── 원소별 합병 → (4,) 하나
    └─ a[1] ── 자식 3개: (4,), (4,), (4,) (동질) ── 원소별 합병 → (4,) 하나

    → 학기마다 (4,) 하나씩 남음 → 결과 shape (2, 4)
    ```

  - **sum(axis=2)** — 2번 층(과목) 접힘 (잎 바로 위 층):

    ```
    root (축0, 학기)
    ├─ a[0]
    │   ├─ a[0,0] ── 잎 4개 (동질) ── 합병 → 스칼라 1개
    │   ├─ a[0,1] ── 잎 4개 (동질) ── 합병 → 스칼라 1개
    │   └─ a[0,2] ── 잎 4개 (동질) ── 합병 → 스칼라 1개
    └─ a[1] ── 위와 같은 구조 (각 학생마다 스칼라 1개씩)

    → 각 (학기, 학생)마다 스칼라 하나 → 결과 shape (2, 3)
    ```

  - ★ **브로의 통일 규약 — '당기기 트리'** (2026-08-30 브로 아이디어): 그림을 그릴 때 **sum 대상 축을 루트로 당겨서** 그리면 규칙이 하나로 통일됨 — "루트 제거 + 직속 자식들(동질) 원소별 합병". 예 — sum(axis=1)을 학생 루트로:

    ```
    root (축1, 학생)          ← 대상 축을 맨 앞으로 당긴 추상 트리
    ├─ s[0] ─ (2,4) 서브트리   ← (학기, 과목) 전체 모습
    ├─ s[1] ─ (2,4) 서브트리
    └─ s[2] ─ (2,4) 서브트리   ← 셋 다 동질 → 원소별 합병 → (2,4) 하나
    ```

    - 이는 개념적 전치(뷰 — 데이터 무동)를 그림 차원에서 수행한 것 — 아래 "전치 경유와 동치"의 시각화 버전이자 "앞축 커널 + 순열" 전략의 다이어그램. NumPy는 실제로 아무것도 당기지 않음 (추상 트리 = 보는 방식의 규약)
    - ★ 주의 — '교환(swap)'이 아니라 '당기기' (2026-08-30 브로 점심 곱씹기): `swap(0, 2)`는 (A,B,C) → (C,B,A)로 **중간 축을 뒤집지만** 당기기는 (C,A,B)로 순서 보존 — k=1일 때만 둘이 동일. 대상이 축2 이상일 때 swap 후 contract하면 남는 축 순서가 뒤집혀 np.sum 결과와 어긋남 (복구 전치가 하나 더 필요)
    - ★ 셋의 포함 관계 (2026-08-30 브로 질문: "당기기와 전치는 뭔 차이?"): **전치** = 축 순서의 임의 재배치 (n! 순열 전부, 전부 strides 재배치 = 뷰) ⊃ **교환** (swapaxes — 둘만 맞바꿈) · **당기기** (moveaxis(x, k, 0) — 하나 뽑아 맨 앞, 나머지 순서 보존). 교환·당기기 모두 전치의 특수 케이스. 실무 등식: `np.sum(np.moveaxis(x, k, 0), axis=0)` ≡ `np.sum(x, axis=k)` — "앞축 커널 + 당기기" reduction 구현의 실체
    - 당기기 순열은 나머지 축의 상대 순서를 보존 → 남는 트리의 축 순서가 np.sum 결과 shape 순서와 정확히 일치
  - 전치 경유와 동치: 목표 축을 루트로 끌어오는 전치를 먼저 하고 합친 뒤 되돌려도 같은 결과 — 전치가 뷰(어드레싱 교체, 데이터 무동)이기 때문. 위 '당기기 트리'가 바로 이 경로의 그림
  - **축소와 축 순열은 서로 교환** — "앞축 커널 하나 + 순열"로 모든 축 reduction을 구현하는 실무 전략과 np.einsum의 사상이 여기서 나옴
- ★ **격자 vs 트리**: 격자 이미지는 전역적 — 3D+에서 사망 (§1 concept image). 트리는 재귀적 — 한 층 = fanout 숫자 하나뿐이라 **차원이 늘어도 난이도 불변**. 그림 탈출구의 다른 출구
- DFS 보너스: 잎을 깊이우선 좌→우로 순회한 순서 = row-major 버퍼 순서. 트리의 각 층 = 축 하나, 간선 = 그 축의 stride 점프 — 어드레싱 세계관(§3~4)과 만나는 지점
- (노트 38 연결) 이 중첩 구조 = 텐서곱의 결합 — $\mathbb{R}^2 \otimes (\mathbb{R}^3 \otimes \mathbb{R}^4)$ 식의 재귀 분해
- (군론 냄새 — 2026-08-30 브로 발견) 가능한 전치 전체 = 축의 순열 전체 = **대칭군 Sₙ**: 전치끼리 합성해도 전치 (닫힘) · 무전치 (항등원) · 같은 순열의 역 (역원)이 존재하는 군. §9의 "역전파 = 역 전치"가 군의 역원 이야기인 것도 이 때문. 노트 38의 모드 회전(순환군 C₇ ⊂ S₇)과 같은 "군 작용" 세계 — 두 노트가 만나는 다리
  - S₂ (2D) — 원소 딱 2개: 항등 `(0,1)` · 교환 `(1,0)`. **2D 전치 세계가 단순했던 이유** — 가능한 전치가 x와 x.T 뿐이라 "접기" 그림 하나로 버틸 수 있었음
  - S₃ (3D) — 6원소 = 항등 1 + 교환 3 + 순환 2: `(0,1,2)` / `(1,0,2)` `(0,2,1)` `(2,1,0)` / `(1,2,0)` `(2,0,1)`. ★ 교환과 순환이 다른 종류 — 순환 2개가 "모드 회전형" (노트 38과 같은 종족), `(2,1,0)`은 교환이면서 3D `.T`의 전축 역순
  - S₄ (4D) — **24원소** (2026-08-30 브로 발견: *"4! = 24, 24개의 축위치 배열이 가능하다고?"*): 4D의 24가지 조직화 전부 공짜(뷰)지만 데이터·정보는 동일 — 폭증하는 건 "읽는 방식의 선택지". ★ 유용한 순열에는 규칙이 있음: **묶음 위계가 연산 방향과 정렬된 것** (채널별 통계 → C 바깥 / 픽셀별 채널 혼합 → C 안쪽) — 연산이 순열을 고른다 (노트 39 Level 3 = 이 유도 기술). 보석: 24 = 4!는 정육면체 회전군의 크기이기도 함 (큐브 회전이 4개 대각선을 순열 → S₄와 동형 — "축 재배치"와 "큐브 회전"이 같은 군)

이제 "전치 = 축 순서의 재배치"가 읽힌다 — **아파트에서 층/호/방의 이름표를 서로 바꾸는 것** (방은 그대로, 주소 체계만 교체).

### 2.1 전치의 정의

- **정의**: 전치 = **축(axis) 순서의 재배치**. NumPy: `transpose(x, axes=(...))`
- ★ axes는 **전체 순열**이어야 함 (2026-08-30 브로 질문): 모든 축을 정확히 한 번씩 지정 — 부분 지정은 에러 ("전치 = 모든 축의 새 자리 배정"이므로). 부분 조작은 전담 도구: `swapaxes`(둘 교환) · `moveaxis`(하나 이동 — §2 피벗 문단). 참고로 `x.T`는 nD에서 **전체 축 역순** 풀순열 (2D에서만 "그 전치"로 보임)
- 2D: `x.T` = `transpose(x, (1, 0))` — "대각선 접기"로 **보이지만** 본질은 축 순서 교환
- 3D: `(2, 3, 4)`에서 `transpose(1, 0, 2)` → `(3, 2, 4)` — **축 0과 1의 역할만 교환**
- ★ **1D는 no-op** (축이 하나라 교환할 짝이 없음) — "열↔행 벡터 전환"은 `(n,1)↔(1,n)`의 **2D 특수 케이스**이지 1D 전치가 아님. 1D를 진짜 행/열로 바꾸는 건 reshape 담당. 행/열은 절대적 속성이 아니라 **관계 개념** (2026-08-30 브로 질문) — 두 번째 축이 있어야 성립하고, 고립된 1D에겐 행/열 질문 자체가 무의미. 다른 배열과 만나는 순간(matmul·브로드캐스팅) 규칙이 해석을 강제 — 4고지 실전
- 고차원 이미지: **"축의 역할 이름 바꾸기"** — 채널축↔공간축, head축↔seq축. 물리적 공간을 상상할 필요 없음 (점검표에서 재확인)

### ★ 3D 양끝 축 맞바꾸기 — transpose(2, 1, 0) (2026-08-28 브로 검증 문항)

> 브로: *"3차원에서 1번째 축과 3번째 축을 바꾼다면? 메모리는 가만히 있는데, 전치 후 주소는?"*

shape (2, 3, 4)에서 축0과 축2를 맞바꾸기 = `transpose(2, 1, 0)`:

- **shape**: (2, 3, 4) → (4, 3, 2) — 양끝만 맞바꿈, **가운데 축1은 구경꾼**
- **주소 대응 규칙**: `a[i, j, k] == b[k, j, i]` — 좌표는 축이 이사 간 자리를 따라감 (i와 k 맞바꿈, j 제자리)
- 아파트로: "1층 2호 0번 방"이 새 주소체계에서는 "0층 2호 1번 방" — 방은 못 갔고 주소만 재발급
- (이 대응이 정말 같은 칸을 찾아내는지의 숫자 검증은 §4로 미룸 — strides를 아직 안 배웠으니 여기선 좌표 규칙만)
- 3D는 축 순서 배치가 3! = 6가지 전부 있는데 `transpose(axes=...)`로 전부 표현 가능 — 축0·축2 맞바꾸기는 `np.swapaxes(x, 0, 2)` 한 방으로도 됨 (§2 국어 사전의 피벗 문단 — moveaxis/swapaxes)
- ★ 2D의 `a[i,j] == b[j,i]`와 **구조 완전 동일** — 좌표가 하나 더 늘었을 뿐. 차원 수는 규칙의 난이도를 바꾸지 않음 (그림의 난이도만 바꿈)

## 3. 메모리의 진실 — 1D 버퍼 + shape + strides

NumPy ndarray의 내부 구조 (명찰의 필드 — 2026-08-30 dtype 추가로 완성):

```
[데이터 버퍼: 1차원 메모리 뭉치]
+ [shape:   축별 길이]          ← 어느 축에 인덱스가 몇 개씩
+ [strides: 축별 보폭(바이트)]  ← 인덱스를 1 늘릴 때 몇 바이트 점프
+ [dtype:   원소 타입]          ← 그 바이트들을 어떻게 읽을지 (한 칸의 크기 + 해석 방식)
```

**stride = 보폭** (영어 뜻 그대로) — 어떤 축으로 인덱스를 1 늘릴 때 메모리에서 건너뛰는 바이트 수.

**dtype과 itemsize** (2026-08-30 브로 질문): dtype은 배열 인스턴스의 속성 (`a.dtype` → `dtype('int64')`) — 버퍼의 날것 바이트를 어떤 타입으로 읽을지 규정. itemsize는 그 dtype의 속성 (`a.dtype.itemsize`) — 원소 1개의 바이트 수 (int64/float64→8, int32/float32→4). strides 초기 계산의 재료.

### 브로의 C 세계와의 재회

```c
int64_t buf[6] = {0, 1, 2, 3, 4, 5};   // 1D 버퍼 6칸 (int64 = 칸당 8바이트)

// ★ 가정: 이 버퍼를 (2, 3) 2D로 해석 — i = 행 인덱스(0~1), j = 열 인덱스(0~2)
// 2D 접근:   x[i][j] = buf[i*3 + j]         ← 브로가 하던 포인터 산술! (3 = 열 개수 — 행 하나 넘을 때 3칸 점프)
// 바이트 주소: addr = base + i*24 + j*8     ← 칸 단위 오프셋에 8바이트를 곱한 것
//                                           24 = 3칸 × 8바이트 (행 전체), 8 = 1칸 (원소 1개)
//                                           ★ 이 계수 (24, 8)이 곧 strides — §4 예시와 같은 숫자
```

- 검증: `x[1][2]` = `buf[1*3 + 2]` = `buf[5]` = 5. 바이트 주소 = base + 1×24 + 2×8 = **base + 40바이트** — §4 구체 예시의 "40바이트"와 동일

- NumPy strides는 이 C 계수를 **축별로 들고 다니며 런타임에 재조립 가능하게 일반화**한 것
- ★ strides는 dtype과 독립적인 **순수 바이트 필드** (2026-08-30 브로 질문) — "타입 크기를 가정해 계산해주는" 게 아니라 관리 단위 자체가 바이트. itemsize는 C-contiguous **초기 strides 계산에만** 기여 (int32 (2,3) → (12,4), int64 → (24,8)). dtype을 몰라 순수 바이트이기 때문에 "같은 버퍼를 다른 dtype으로 읽는 view"가 strides 재계산과 자유롭게 조합됨 — 아래 캐스팅 ↔ view 대응의 비밀 (C의 `p+1`은 컴파일러가 타입을 보고 바이트를 곱해주는 신택틱 슈가, NumPy는 그 곱셈 결과를 명찰에 저장)
- ★ **shape의 이중 역할 분리** (수술의 핵심 중 하나):
  - **총량** (2×3=6) → 버퍼 크기에만 기여 — (2,3)이든 (3,2)든 (6,)이든 같은 48바이트
  - **구조** (2,3 순서) → strides 초기값에만 기여 (C순서 default)
  - 이 분리("버퍼=총량의 세계 / shape+strides=해석의 세계")가 view 전치의 비밀
- ★ **두 세계의 함정 — NumPy vs PyTorch** (2026-08-30 브로 질문으로 확장):
  - 단위: NumPy는 **바이트** (`(2,3)` int64 → strides `(24, 8)`), PyTorch는 **원소 수** (`(3, 1)`) — 같은 정보의 관례 차이일 뿐, 환산식 `torch stride × itemsize = numpy strides` (3×8=24, 1×8=8)
  - 접근자 이름도 다름: `a.strides`(numpy) vs `t.stride()`(torch) — 문서·포팅에서 숫자가 itemsize배만큼 어긋나 보여 혼란의 온상
  - 정체: 파이토치는 NumPy 위가 아니라 **독립 구현** (C++ ATen 코어). 근거: **NumPy는 CPU 전용** — GPU(CUDA) 메모리 모델도 autograd도 없어서 감쌀 수 없음. API는 의도적 NumPy 계승. (GPU에서 numpy 스타일을 쓰는 별도 독립 구현이 CuPy — 정답지 `dezero/cuda.py`가 GPU일 때 부르는 게 그것, 없으면 NumPy로 fallback)
  - 상호 전환은 실무 일상: `torch.from_numpy(a)` / `t.numpy()` — CPU에서는 **제로 카피 메모리 공유** (view 관계 — 한쪽 수정이 양쪽 반영), GPU 텐서는 `.cpu()` 후에만
  - 기본 dtype도 다름: numpy float64, torch float32

### ★ C++ 표현 3가지와의 매핑 — 브로 혼란의 숨은 원인 (2026-08-28 질문에서)

> 브로: *"C++에 정적 배열, 래그드 어레이, 1D 버퍼+포인터 계산 등 여러 방식이 있는데 그게 다차원 전치 이야기와 섞여 완전히 헷갈렸다."*

| C++ 방식 | 메모리 | stride 모델 |
|---|---|---|
| 정적 배열 `int a[2][3][4]` | 연속 — strides 컴파일타임 고정 | O (NumPy의 조상, 단 재조립 불가) |
| **래그드(ragged)/재그드(jagged) 배열** (`int**`, 행별 할당) | **비연속!** 행마다 별도 버퍼, 크기 들쭉날쭉 가능 | ✗ **적용 불가** — NumPy ndarray는 ragged가 아님 |
| 1D 버퍼 + 수동 계산 `buf[i*N+j]` | 연속 | O — strides를 손으로 계산하는 것 |

★ 래그드 배열은 "다차원"처럼 보이지만 stride 모델이 통하지 않는 **완전히 다른 구조** — 세 가지가 한 서랍에 있으면 혼란. NumPy ndarray는 언제나 **연속 버퍼(또는 그 view)**. 용어 2형제 (2026-08-28 브로 질문): **jagged(재그드)**가 C#/Java 주류 용어("톱니 모양" — C# 공식 문서), **ragged(래그드)**가 과학계산 쪽 애용("너덜한 가장자리") — 뜻은 같은 개념.

### ★ std::vector — 이름의 역설과 1축 ndarray (2026-08-28 저녁 수다)

> 브로: *"std::vector는 내부가 1차원 선형 메모리 베이스 주소를 포인팅한다? 이 이름이 쌩뚱맞기도 하면서 또 벡터적(선형대수적)이기도 하고..."*

**구조**: 필드 3개 — {시작 포인터, size, capacity} = "버퍼 + 명찰". ndarray 문법으로 번역하면:

```
std::vector<double> v(n)
  = shape (n,)      ← 축 하나
  + strides (8,)    ← double 보폭, 하드코딩
  + 1D 버퍼 포인터
```

- **이름의 역사**: 수학 벡터(ℝⁿ 원소 = 순서 있는 성분 튜플)에서 따온 이름 — 스트라우스트럽 본인이 아쉬운 네이밍이었다고 FAQ에서 인정한 것으로 유명. 다른 언어는 정신 차림(Java `ArrayList`, Python `list`, Go `slice`) — Rust `Vec`은 C++에서 이름을 물려받음. 수치계산용 `std::valarray`가 따로 존재하는 것도 혼란의 흔적
- ★ **어드레싱 관점에서는 이름이 오히려 정당**: 수학 벡터 = 축 하나짜리 배열 그 자체. `vector<double>(n)` = shape (n,), strides (8,)인 1축 ndarray = ℝⁿ의 가장 순수한 구현. "벡터는 다차원이 아니라서 이름이 이상"이 아니라, **벡터는 원래 1축이고 다차원이 확장**인 것
- ★ 결정적 차이: std::vector는 strides를 **소유하지 않음** (연속성에 하드코딩) → strides 재조립(전치) 불가. 그래서 C++에서 2D를 하면 `vector<vector<double>>`를 쓰게 되는데 — 바로 위 표의 **래그드 함정** 그 자체

### ★ &v[0] + 캐스팅 — C 세계의 view/reshape (같은 수다)

> 브로: *"'&v[0]'로 선두 주소 획득 후 임의의 포인터 타입으로 캐스팅 — 이게 넘파이로 치면 shape 변경 느낌?"*

| C/C++ | NumPy | 하는 일 |
|---|---|---|
| `reinterpret_cast<NewT*>(buf)` | `arr.view(new_dtype)` | 같은 버퍼, **원소 단위(스케일)** 재해석 |
| `reinterpret_cast<int(*)[4]>(buf)` 후 `p[i][j]` | `arr.reshape(-1, 4)` | 같은 버퍼, **좌표계(축 구조)** 부여 |
| `buf[i*NCOLS + j]` | strides (4, 1) 수동 계산 | 혼합 진법 어드레싱 (위 "C 세계와의 재회") |

(-1 표기: **"이 축 크기는 알아서 계산"** — 24칸 버퍼를 `reshape(-1, 4)`하면 (6, 4). 한 축에만 쓸 수 있음. 상세는 §4 reshape 해부)

- 강제 캐스팅 = **"데이터 무동, 해석 규칙만 교체"** — §5 관찰자 이동의 C 버전 (타입 시스템을 우회하는 수동판)
- NumPy는 이걸 객체 안으로 들여와(명찰 소유 + 경계 검사) **통제된 캐스팅의 세계**로 만든 것. 반대로 말하면 **C는 모든 것이 as_strided인 세계** — 자유의 대가: strict aliasing 규칙, 정렬, 크기 검증이 전부 프로그래머 몫 ("물론 안전하게 해야겠지만" — 브로)
- 캐스팅 = 단위계(스케일) 변경, reshape = 좌표계 재편 — 둘 다 "같은 데이터를 다른 선형 사상으로 읽기"

### ★ "첫 차원이 가장 큰 차원?" — 길이와 보폭의 분리

`a[2][3][4]`의 첫 축: **길이는 2 (가장 작음!), 보폭은 최대** (한 걸음에 나머지 3×4=12칸 점프). "큰 차원"의 뜻을 길이로 잡으면 첫 축은 최소, 보폭으로 잡으면 최대 — 이 둘이 섞이면 혼란의 씨앗.

- ★ 어휘 정리 (2026-08-30 브로 질문: *"축1이 축2보다 고차원이라는 표현이 맞나?"*): **고차원/저차원은 배열 전체의 속성** (ndim 수 — "4차원 배열은 고차원" O)이지 축 개별 비교에 쓰는 말이 아님 (X). 같은 배열의 축들은 동격 — 같은 공간의 좌표 방향. 축끼리 비교하는 올바른 어휘는 **길이**(인덱스 수) · **보폭**(점프 크기) · **바깥/안 축**(outer/inner — 축0이 가장 바깥·트리 루트, 마지막 축이 가장 안 = 가장 빨리 변하고 메모리에 인접). 브로 원래 혼란("첫 차원이 가장 큰 차원?")의 정체: 길이(축들 중 **최소** — 2 vs 3, 4) + 보폭(축들 중 **최대** — 12 vs 4, 1칸) + 바깥 축이라는 위상이 "크다" 한 단어에 뒤엉킨 것 — 같은 축을 길이로 재면 제일 작고 보폭으로 재면 제일 큼

### ★ strides의 정체 — 혼합 진법(mixed-radix) 수 표기 (2026-08-28 대화)

오프셋 공식 `i×s₀ + j×s₁ + k×s₂`는 사실 **(i, j, k)를 세 자릿수로 하는 혼합 진법 숫자 계산** — 자리마다 밑이 다른 진법 (십진법의 일반화):

- (2, 3, 4) 배열의 row-major: s₂ = 1, s₁ = 4, s₀ = 12 — "일의 자리는 4바닥, 십의 자리는 3바닥, 백의 자리는 2바닥"인 숫자
- **일상의 혼합 진법 = 시계**: (시, 분, 초) = (24, 60, 60)바닥 세 자릿수. "1일 3시간 25분"을 초로 환산하는 `1×86400 + 3×3600 + 25×60`이 곧 strides 곱셈 (1일 = 86400초가 stride)
- ★ 즉 "인덱스 튜플을 한 줄(1차원)로 펴는 규칙"은 컴퓨터가 없어도 인류가 써온 기술 — 단, 수학 세계에서는 개념의 일부가 아니라 **선택사항** (§7의 생존표와 칸토어 대각선 참조)
- 파생 지도 (2026-08-30): [탐구 노트 38 — 혼합 진법에서 FFT와 화성학까지](./exploration_38_mixed_radix_fft_music.md) — 혼합 진법의 선형대수(쌍대·CRT·텐서곱·FFT)와 음악 7모드(회전 뷰)로 확장. 브로 아침 망상("모드가 축교환 느낌?")이 착상

## 4. 전치의 실체 — strides 재배치 (view)

transpose가 하는 일은 **strides 튜플의 순서만 재배치**:

```python
x     # shape (2, 3), strides (24, 8)
x.T   # shape (3, 2), strides (8, 24)   ← 버퍼 무동!
x.T.base is x   # True — view (복사 아님)
# 1000×1000 전치도 ~3e-07초 — O(1) (데이터 크기 무관)
```

### ★ view의 3요소와 자기 검증 (2026-08-28 대화)

> 브로: *"transpose가 리턴하는 뷰는, 전치된 strides 정보가 들어가 있다는 상황이군?"*

정확 — transpose가 반환하는 view는 **"새 명찰(배열 객체) 하나 + 같은 버퍼"**. 명찰에 적힌 것:

- **shape**: 전치된 shape
- **strides**: 전치된 strides
- **버퍼 포인터**: 동일 (복사 0바이트)
- **dtype**: 그대로 — 전치가 바꾸는 건 shape과 strides뿐 (dtype을 바꾸는 view는 별개 이야기 — §3 캐스팅 대응)

```python
import numpy as np

a = np.arange(24).reshape(2, 3, 4)
b = a.transpose(2, 1, 0)

b.strides       # (8, 32, 96)  ← 전치된 strides (바이트 단위; 칸 수 (1, 4, 12) × 8바이트)
b.shape         # (4, 3, 2)
b.base is a     # True — 같은 버퍼 공유
b[0, 0, 0] = 999
a[0, 0, 0]      # 999 — b를 고쉬면 a도 변함 (몸통이 하나라는 증거)
```

- 마지막 두 줄이 view의 서약 — 값을 통한 수정이 원본에 반영됨. 데이터 복사가 없으니 당연
- strides가 칸 수가 아니라 **바이트 수**라는 점 재확인 (§3의 단위 주의 — int64라 칸당 8바이트)

### ★ "축을 바꾸면 원소 수가 변동?" → 아니 — (길이, 보폭) 묶음의 자리 이동

예시 배열을 하나 정의한다 — int64 6개짜리 (2, 3) (아래 "구체 예시"에서도 이 배열을 그대로 씀):

```
x = [[10, 20, 30],
     [40, 50, 60]]    # shape (2, 3), strides (24, 8) — int64라 칸당 8바이트

x.T                   # shape (3, 2), strides (8, 24)

x   : 축0 = (길이 2, 보폭 24)   축1 = (길이 3, 보폭 8)
x.T : 축0 = (길이 3, 보폭 8)    축1 = (길이 2, 보폭 24)
      ↑ (길이 3, 보폭 8) 묶음이 통째로 축0으로 이사 — 내용물 그대로
```

- 총 원소·메모리 배치·최대 도달 오프셋 전부 불변:
  - shape/strides 대조: `(2,3)/(24,8)` ↔ `(3,2)/(8,24)` — 같은 버퍼, 묶음의 배정만 교체
  - 마지막 원소 위치로 검증: `x[1,2] = 1·24 + 2·8 = 40` = `x.T[2,1] = 2·8 + 1·24 = 40바이트`

### ★ "오프셋 보정을 누적 추적?" → 그런 시스템 자체가 없음

모든 원소 참조는 매번 **한 줄 공식**: `addr = base + Σ(인덱스 × 보폭)`.

`addr(i, j)`와 `addr'(j, i)`가 같은 주소가 되는 건 **곱셈 교환법칙** — 같은 두 항의 합에 인덱스 이름만 교환된 것. "보정"이 아니라 **공식의 대칭성**.

### 구체 예시 (숫자로 못박기)

x = `[[10, 20, 30], [40, 50, 60]]` — 위 섹션의 그 배열 ((2, 3), int64, strides (24, 8)). 버퍼를 펼쳐 놓은 모습 (**값@번지** 표기 — `10@0`은 "0번지에 값 10", 한 칸 = 8바이트):

```
버퍼:      10@0  20@8  30@16  40@24  50@32  60@40    ← 1D로 깔린 실체

x[1,2]   = 1×24 + 2×8 = 40번지 → 60
x.T[2,1] = 2×8  + 1×24 = 40번지 → 60   ← 값도 주소도 같은 칸
```

- ★ **축이 주소를 소유하는 게 아니다** — (인덱스 조합 → 주소) 매핑이 strides로 정의될 뿐. 전치는 그 정의식의 계수 순서를 바꾸는 것. 유지되는 건 버퍼의 값뿐이고 그건 애초에 무동.
- ★ 반대 방향 확인 ("역방향 증명"의 뜻, 2026-08-30 브로 질문): 위 계산은 "전치 뷰가 같은 칸을 찾는다"(정방향) — 반대로, 전치를 "접어서 다시 그린 종이"처럼 **C연속 배열로 실체화**하려면 **copy 필요**. 증거: `x.ravel()` = [10, 20, 30, 40, 50, 60] vs `x.T.ravel()` = [10, 40, 20, 50, 30, 60] — 전치 뷰를 C순서로 순회하면 칸을 뛰어다녀야 해서 새 버퍼에 다시 깔아야 함 (§6 ascontiguousarray가 copy를 동반하는 이유)

3D 에코 — §2.1에서 미뤄둔 숫자 검증 (`transpose(2, 1, 0)`, 단위: 칸):

```
a        # shape (2, 3, 4), strides (12, 4, 1)
b        # shape (4, 3, 2), strides (1, 4, 12)   ← 양끝만 맞바꿈, 가운데 보폭 4는 제자리

a[1,2,0] = 1×12 + 2×4 + 0×1 = 20번 칸
b[0,2,1] = 0×1  + 2×4 + 1×12 = 20번 칸   ← §2.1의 주소 대응 a[i,j,k] == b[k,j,i] 검증 완료
```

- ★ 2D 예시와 **구조 완전 동일** — 좌표와 계수가 하나씩 늘었을 뿐. 차원 수는 규칙의 난이도를 바꾸지 않음

### ★★ 어드레싱의 선형대수 — offset은 인덱스와 strides의 내적 (2026-08-28 저녁 수다)

> 브로: *"strides는 '가중치' 느낌도 있고... 가중치가 곱해진 좌표, '결합'의 느낌 — 왠지 선형대수를 떠올리게 된다."*

정확한 직관 — 오프셋 공식은 **인덱스 벡터와 strides 벡터의 내적**:

$$\text{offset} = i{\cdot}s_0 + j{\cdot}s_1 + k{\cdot}s_2 = \langle (i,j,k),\ (s_0, s_1, s_2) \rangle$$

- 어드레싱은 **선형 사상** (정확히는 base 오프셋이 붙은 아핀 사상) — 행렬 표현은 diag(s₀, s₁, s₂) 대각행렬. §7의 "선형 사상 vs 행렬"이 어드레싱 공식에도 출현
- ★ **전치가 같은 칸을 찾는 가장 깊은 이유**: 전치는 인덱스와 strides **둘 다에 같은 순열 P를 적용**하는 것 — 순열 행렬은 직교(PᵀP = I)라 내적이 보존됨: $\langle P\,\text{idx},\ P\,\text{strides} \rangle = \langle \text{idx},\ \text{strides} \rangle$
- 위 "곱셈 교환법칙"(성분 뷰)의 **좌표 없는 버전** — §9의 ⟨Aᵀy, x⟩ = ⟨y, Ax⟩와 같은 종족 ("자리를 바꿔도 내적이 보존된다"가 이 노트의 하루 대주제)

### ★ strides의 자유도 — 음수, 0, 겹침 (4고지 복선)

NumPy 세계에서 이 "가중치"는 자유롭다:

- **음수**: `x[::-1]` — 반전 뷰 (뒤에서 앞으로 걷는 보폭)
- **0**: 원소를 무한 복제해 보이는 뷰 — **4고지 step40 `broadcast_to`의 비밀** (브로드캐스팅이 메모리 복사 없이 stride 0으로 구현됨)
- **겹침**: 같은 칸을 여러 축이 공유하는 뷰 — `numpy.lib.stride_tricks.as_strided`가 임의 strides 설치를 허용하는 위험한 문 (경계 검사 없음 — C 세계의 자유를 다시 주는 문, §3의 "모든 것이 as_strided" 참조)

### ★★ "선언의 차원 순서 바꾸기" ≠ 전치 (핵심 교정, 2026-08-28 브로 질문에서)

> 브로: *"`int arr[2][3][4]`을 `int arr[4][3][2]`로 바꾸는 건 전치가 아니잖아? 이게 내 혼란 포인트와 섞여 있을지도."*

**정확한 지적 — 이건 전치가 아니라 별개의 새 배열이다:**

```
a = int[2][3][4]           strides (48, 16, 4)   ← C순서 계산
a.transpose(2,0,1)         shape (4,2,3), strides (4, 48, 16)  ← 같은 버퍼 재배치 ★전치★
b = int[4][3][2]           strides (24, 8, 4)    ← 다른 버퍼, 새로 C순서 계산 ★별개 배열★
```

- b는 shape 숫자 나열이 우연히 반대 **순서일 뿐** — strides 구성이 전혀 다름
- **전치 = 같은 버퍼 + strides 재배치 / 선언 변경 = 다른 버퍼 + 새 strides**
- ★ 브로 혼란의 뿌리: "차원 크기 나열 바꾸기"(선언)와 "축 순서 재배치"(전치)가 머릿속 같은 서랍에 있었던 것 — NumPy에서 shape을 바꾸는 연산은 reshape(버퍼 재해석, 조건부 view)이지 전치가 아님.

### ★★ reshape 해부 — 같은 버퍼, 같은 순서, 다른 자르기 (2026-08-30 브로 질문 4연타)

- **arange(24)의 정체**: 버퍼 24칸 + shape (24,) + strides (8,) — 1축 배열. 표기 주의: shape (24,)의 쉼표는 "튜플" 표기 — "(1,)"은 "길이 1 배열"이라는 뜻이지 "1차원"이 아님
- **reshape = 차원 정보 가공** — 버퍼 무동, shape 교체 + strides 재계산 (C순서 기준). "24칸을 (2,3,4)로 자르는 설계도 교체" — 이 노트 관점에서 reshape도 관찰자 이동(§5)의 한 종류
- ★ **총량 불변의 율법**: 새 shape의 곱이 원소 수와 같아야 함 (2×3×4=24). 어긋나면 `ValueError: cannot reshape array of size 24 into shape (2,3,5)`. 데이터 수 자체를 늘리는 건 reshape의 관할 밖 (resize·concatenate·pad의 담당)
- `-1` 관례: 한 축에만 쓸 수 있는 "남은 축 알아서 계산" — `x.reshape(2, -1)` → (2, 12)
- ★ **축 개수(ndim)는 자유** (2026-08-30 브로 질문): 곱만 맞으면 (24,) ↔ (2,12) ↔ (2,3,4) ↔ (1,24) 전부 가능. 크기 1 축은 곱에 기여 안 하므로 공짜 껍데기 — `(N,) ↔ (N,1) ↔ (1,N)` 왕복이 ML 현장의 일상이고 `np.squeeze` / `np.expand_dims`(또는 `x[:, None]`)가 전담. 수학적 얼굴 = 같은 공간의 임의 텐서곱 분해 (노트 38 §2.4). 단 **기계적 자유 ≠ 의미론적 자유** — reshape는 축의 역할 이름표를 모름: (학기,학생,과목)을 (6,4)로 묶으면 이름표는 사라지고 해석은 분석가 몫
- ★★ **reshape로 전치를 대체할 수 있나? → 없다 (뷰로는)**:
  - reshape는 **선형 순서를 보존** — 메모리 0번 칸부터 읽는 순서 그대로, 묶음 단위만 바꾼다
  - 전치는 **선형 순서를 재해석** — 같은 칸들을 다른 순서로 읽게 strides를 재배치
  - 그래서 전치 뷰는 reshape로 표현 불가. 전치된 "진짜 C연속 배열"이 필요하면 copy가 필수 — `np.ascontiguousarray(x.T)` (§6의 재미 연결 그것, §4 역방향 증명의 이유)
  - ★ 실전 예고: PyTorch의 `.view()`는 연속(contiguous) 텐서에만 동작 — 전치 직후 `.view()`를 부르면 에러를 뿜고 `.contiguous()`를 먼저 하라고 안내함. "전치(뷰) + view(연속 요구) + copy"의 삼각관계를 실무에서 맞닥뜨리는 지점

### ★ 두 클럽 마무리 — 데이터 무동(뷰) vs 계산(reduction) (2026-08-30 브로 혼동 정리)

> 브로: *"당기기나 전치나 — 전체 요소 수를 안 바꾸고 보는 관점만 달라진다, 즉 어드레싱만 바뀐다는 점에서는 같다는 소리지? 물론 최종 참조 인덱스 순서가 바뀌어서 주의해야 하지만."* — 정확. 당기기·교환·임의 전치는 전부 같은 클럽.

| 클럽 | 회원 | 하는 일 | 비용 |
|---|---|---|---|
| **데이터 무동 (뷰)** | 전치 가족 (전치·교환·당기기), reshape | **안경 갈아끼우기** — 어드레싱(해석 규칙)만 교체 | O(1), 버퍼 무동, 요소 수 불변 |
| **계산 (reduction)** | sum·max·min·mean·prod (contraction 가족) | **실제로 요약 계산** | 새 버퍼, 요소 수·축 수 감소 |

- 공통 주의 (브로 지적): 뷰 클럽 안에서도 **같은 원소를 가리키는 인덱스 조합은 바뀜** — `a[i,j,k]`가 순열된 좌표로 읽혀야 하고, reduction과 조합 시 survivor 순서 문제(swap vs 당기기 — §2 트리)가 생김
- 이 표가 §2의 "sum의 정체"(축 수는 규칙 교체로 못 줄임), §4의 view 3요소·reshape 해부, §2 트리의 당기기 규약을 한 장으로 묶는 지도 — 데이터는 늘 무동, 움직이는 건 관찰자 (§5)

<a id="관찰자비유"></a>
## 5. 관찰자 비유 — 종이는 그대로, 내가 움직인다

> 브로: *"종이인쇄된 2D 행렬을 종이 자체는 그대로 두고, 그 주위를 내가 움직여서 다른 식으로 보는 것?"*

정확한 비유. **관찰자 위치 = 어드레싱 규칙.** 전치는 종이(버퍼)를 조작하는 게 아니라 관찰자(규칙)가 자리를 옮기는 것. 종이 그림 교육은 "종이를 다시 그리는" 관점이었고, stride 세계는 "관찰자가 걸어다니는" 관점.

### ★ 브로의 관점 전환 순간 — 실측 기록 (2026-08-28)

> 브로: *"자꾸 머리에서 뭘 그리려 하는데, 걍 1차원 겁나 긴 놈이라 생각하면... 1차원 상의 특정 위치에 똬~악 매칭되는구만?"*

```
머리가 하려던 것: 3D 큐브를 머릿속에서 돌리고 접고      ← 이걸 포기하는 순간
실체:            [0][1][2][3]...[23] 겁나 긴 한 줄     ← 배열의 진짜 몸통
부속품:          (shape, strides) 얇은 안내서           ← 인덱스 읽는 법
전치:            안내서 숫자 몇 개 맞바꾸기              ← 끝. 몸통 무변동
```

인덱싱의 실체도 동일 — `a[i,j,k]`를 받은 NumPy는 strides 안내서대로 `i×s₀ + j×s₁ + k×s₂`를 계산해 그 한 칸을 읽을 뿐. "그림을 그리려다 포기하고 규칙으로 전환"한 이 순간이 이 노트 전체의 목적지 — §1의 concept image 문제와 §7의 이중성이 만나는 지점.

<a id="두파벨"></a>
## 6. 배치 순서의 두 파벨 — row-major vs column-major

같은 (2,3) 배열도 버퍼에 깔리는 순서가 두 파벨:

| 파벨 | 첫 인덱스의 보폭 | 채택 |
|---|---|---|
| **row-major (C 순서)** | 최대 — 나머지 영역 전체 점프 (`[i][j]`의 i가 행, 행 전체를 뛰어넘음) | C, C++, **NumPy 기본** (`order='C'`) |
| **column-major (F 순서)** | 최소 — 다음 원소 (Fortran `A(i,j)`의 i가 열) | Fortran, MATLAB, R |

- C++ 다차원 배열 문법은 **신택틱 슈거**: `a[i][j]` → `*(base + i*3 + j)` (컴파일러가 계수 계산) — shape 컴파일 타임 고정이라 재조립 발상이 필요 없었던 세계
- ★ 재미 연결: **C순서 행렬을 전치된 어드레싱으로 보는 것 ≈ F순서로 보는 것** — 전치와 배치 순서가 만나는 지점. `np.ascontiguousarray(x.T)`는 copy를 동반하는 이유도 여기 (C순서로 다시 깔아야 하니까)
- 어원 보석 (2026-08-28 브로 질문): "파벨"은 **파벌(派閥)**의 커뮤니티식 표기 — 벌(閥)은 재벌(財閥)·문벌의 그 벌. "큰 집단 안에서 끼리끼리 모이는 패거리"라는 뜻으로, 두 배치 순서 진영이 각자의 기본값을 사수하며 수십 년째 대립하는 뉘앙스를 노리고 채택한 표기

<a id="이중성"></a>
## 7. 두 세계의 이중성 — 수학엔 메모리가 없다

> 브로: *"수학적 다차원은 메모리 개념이 없는데, 물리 메모리 지식이 혼란을 유발"*

정확한 자기 진단. 이 이중성은 이 프로젝트의 반복 테마:

| 세계 | 다차원의 모습 | 전치의 의미 |
|---|---|---|
| **수학** ($\mathbb{R}^n$) | 좌표 추상 — 순서 없음, 메모리 없음 | 관계(재배치)만 존재 |
| **구현** (메모리) | 1D 버퍼 + 어드레싱 — **배치 순서 필연** | strides 재배치 (view) |

- 수학엔 "누가 먼저 저장됐나"라는 질문 자체가 없음. 구현은 버퍼가 1D라 순서가 강제로 생김.
- 두 세계를 오가는 **번역 규칙이 shape/strides** — 혼란은 국경에서 발생 (브로가 겪은 것)
- 같은 이중성의 발현: 노트 34 §5 (명세 vs 실행 — VJP와 전치 둘 다), 노트 35 §9 (구현 텐서 vs 수학 텐서). **세 번째 만남이 여기.**

### ★★ 수학자의 전치 — 그림이 아니라 구조로 정의된다 (2026-08-28 질문: "컴퓨터가 없었다면?")

> 브로: *"수학자들은 메모리를 생각조차 안 했을 것 아닌가. 그럼 어떻게 생각했을까? shape, 원소 수, 좌표, strides 같은 개념이 수학 세계에서도 유효한가?"*

수학자는 전치를 "접어서 다시 그리기"로 정의한 적이 없음 — **선형 사상의 언어**로 정의:

$$\langle A^T y,\, x \rangle = \langle y,\, Ax \rangle$$

- "입력·출력 자리를 바꿔 대입해도 내적이 보존되는 사상"으로 Aᵀ를 규정 (쌍대 사상/수반 사상이라 부름)
- 성분 버전 $(A^T)_{ij} = A_{ji}$는 이 구조의 **좌표 표현**일 뿐
- 고차원(텐서)도 동일 — 인덱스 순서 바꾸기 = 다중선형 사상의 **인수 자리 맞바꾸기**: $B(x_2, x_1, x_3) = A(x_1, x_2, x_3)$
- ★ 선형 사상(구조) vs 행렬(좌표 표현)의 관계가 전치에도 그대로 — "종이 접기"는 좌표 표현의 2D 시각화에 불과했던 것

### ★ 컴퓨터를 제거했을 때 — 개념 생존표 (브로 질문에 대한 직답)

| 개념 | 수학 세계에서 |
|---|---|
| shape | ✅ 생존 — "크기 n₁×n₂×n₃인 지표 순서쌍들의 집합" |
| 원소 수 | ✅ 생존 — 순수 조합론. 축 순열은 인덱스 집합 위의 전단사 |
| 좌표 | ✅ 생존 — 인덱스 (i, j, k)는 그냥 순서쌍 |
| **strides** | ❌ **소멸** — "순서쌍 집합을 1차원 한 줄로 펴는 규칙"이라 저장(메모리)이 등장해야만 필요해지는 개념 |

- 수학자도 줄세우기가 필요할 때는 했음 — 사전순 배열, **칸토어의 대각선 훍기** (ℕ×ℕ의 크기를 셀 때). 흥미롭게도 칸토어 대각선은 row-major와 **다른 선형화** — 둘 다 정당한 전단사
- ★ 즉 **선형화는 진리가 아니라 선택** — 구현 세계에서 그 선택이 strides라는 숫자로 강제될 뿐 (§3의 혼합 진법 참조)

<a id="실전지도"></a>
## 8. 실전 지도 — 3D+ 전치가 매일 일어나는 곳

> 표기: "3D+" = **3차원 이상 전부** — '+'는 "그 이상 전부" 뜻의 줄임 ("19+", "iOS 15+"와 같은 패턴).

| 사례 | 전치 | 차원 |
|---|---|---|
| PyTorch(CHW) ↔ TF/NumPy(HWC) 이미지 변환 | `(H, W, C) ↔ (C, H, W)` | 3D |
| 배치 이미지 | `(B, C, H, W)` 정렬/재배치 | 4D |
| Transformer 어텐션 | `(B, S, H, D) → (B, H, S, D)` — head 축 앞으로 | 4D |
| CNN (5고지) | 합성곱 축 정렬, im2col 전후 | 4D+ |

- 밑시딥3 타임라인: **reshape/transpose = step38, sum = step39, broadcast_to/sum_to = step40, matmul = step41** — 4고지가 이 순서로 "구조 연산도 미분 가능"을 펼침 (노트 35 §4와 1:1)

### ★ NCHW 재조직화 — 큐브 나열의 축 바꾸기 (2026-08-30 브로 관찰)

> 브로: *"(N,C,H,W)를 큐브의 나열로 그렸는데, N과 다른 축을 바꾸니 채널별로 묶인 큐브가 나열되더라? 이게 맞아?"* — 맞음, 전치의 정확한 효과.

- (N, C, H, W): **이미지별 큐브 나열** — 각 큐브(이미지) 안에 채널들이 순서로
- (C, N, H, W)로 바꾸면: **채널별 큐브 나열** — R그룹(N장의 R 평면을 쌓은 큐브) → G그룹 → B그룹. 성적표 (학기,학생,과목) ↔ (학생,학기,과목) 재조직화와 동형 — 같은 데이터, 묶음의 위계만 교체 (트리에서 N층·C층 순서 교환)
- 실전 의미: PyTorch **NCHW** vs TensorFlow **NHWC** 레이아웃 대립 (서로 전치 관계 — 이식 시 관례 충돌의 주범). 채널별 연산(예: BatchNorm의 채널별 통계)은 채널 축을 바깥으로 당기면 reduction이 자연스러워짐 — §2 당기기 원리의 실전 등장

### ★ n차원 시각화 관례 — 큐브 배치도 (같은 날 브로 발견)

- nD 배열을 그리는 표준 전략: **잎을 3D 큐브로 두고 나머지 (n-3)개 축은 큐브의 "배치도"** — 4D = 큐브의 1D 나열, 5D = 큐브의 2D 격자, 6D = 큐브의 3D 격자, 그 위로는 재귀
- 실제 관례들: matplotlib subplots 격자, torchvision `make_grid`, NumPy의 ND print(2D 블록의 중첩 리스트 인쇄) — 전부 이 원칙
- ★ 전체를 한 장에 그리는 건 포기하고 "조직도(바깥 축) + 잎(큐브)"로 나누는 것 — concept image(§1) 탈출의 표준 출구이자 트리 뷰(§2)의 시각화판
- 파생 연습장 (2026-08-30 브로 요청): [탐구 노트 39 — 고차원 전치 연습장](./exploration_39_highdim_transpose_gym.md) — 4D·5D 묶음 읽기 훈련 (서류 재철 비유 + Level 1~4 문제). 4고지 step38 직전이 최적 타이밍

<a id="역전파연결"></a>
## 9. 역전파와의 연결 — 뷰 규칙의 왕복

- transpose의 VJP = **역 transpose** (gradient에 같은 축 교환을 다시 적용)
- stride 관점: forward에서 바꾼 strides 순서를 backward에서 되돌리는 것 — **데이터가 아니라 뷰 규칙을 왕복**
- reshape도 마찬가지 (역 reshape). 구조 연산의 역전파가 전부 "역 재배치"인 이유 — 명세(재배치된 행렬)와 실행(stride view)이 다르지만 backward는 실행 규칙을 그대로 뒤집으면 되는 것
- 이것도 "야코비안(치환행렬)을 만들지 않는다" (노트 34)의 한 사례

### ★★ (Ax)·y = x·(Aᵀy) — 성분 전개로 유도된다 (2026-08-28 브로 질문)

> 브로: *"이 표현은 좌측 식에서 우측 식으로 원래 자연스럽게 유도가 가능한 것이었어?"*

가능 — **성분 전개 → 덧셈 순서 교환 → 재묶음** 세 단계뿐:

$$
(Ax)\cdot y
= \sum_i \Big(\sum_j A_{ij} x_j\Big) y_i
= \sum_i \sum_j A_{ij}\, x_j\, y_i
= \sum_j x_j \Big(\sum_i A_{ij}\, y_i\Big)
= \sum_j x_j\, (A^T y)_j
= x \cdot (A^T y)
$$

- 핵심 한 걸음: 유한 합의 순서 교환 (ΣᵢΣⱼ → ΣⱼΣᵢ) — 곱셈 교환법칙만큼이나 "특별한 것 없음"
- 안쪽 합 $\sum_i A_{ij} y_i$가 정확히 $(A^T y)$의 j번째 성분 — 전치의 정의가 유도 중간에서 자동 출현
- ★ 방향성은 양방향: "성분 뒤집기로 Aᵀ 정의 → 내적 보존 증명"도 되고, 반대로 "내적 보존으로 Aᵀ 규정 → 성분 뒤집기 도출"도 됨 (§7 수학자 정의와 잇는 닭-달걀)
- 실용적 마법: **식을 계산하기 편한 쪽으로 옮겨 담을 수 있다** — 역전파에서 전치가 맨날 튀어나오는 이유. 4고지 MatMul backward의 `gy @ W.T`가 이 성질의 현현 (step41에서 회수)

### ★ 4고지 예고 — 미분 = 선형 근사, 그리고 전치와의 재회 (2026-08-28 대화)

> 브로: *"'미분 = 선형 근사(야코비안)' — 벡터함수의 도함수가 야코비안이라서? 벡터함수라 부른 함수의 도함수 표현을 제대로 본 적이 없다."*

정확하며 한 겹 더 정밀하게:

- **정의 (프레셰 미분)**: $f: \mathbb{R}^n \to \mathbb{R}^m$이 x에서 미분 가능 = 선형 사상 L이 존재해 $f(x+h) = f(x) + L(h) + o(\|h\|)$. **미분 = 그 선형 사상 L 자체**
- **야코비안** = L의 표준기저 행렬 표현 (m×n, $J_{ij} = \partial f_i / \partial x_j$) — "선형 근사 ≒ 야코비안"은 사상과 행렬을 좌표계 안에서 동일시하는 편한 말
- 예: $f(x, y) = (xy,\, x+y)$ → $J = \begin{pmatrix} y & x \\ 1 & 1 \end{pmatrix}$
- 1차원(n=m=1): $L(h) = f'(x)\,h$ — **"접선의 기울기"는 선형 사상의 1×1 특수 케이스**. 그림이 없어져도 정의는 멀쩡 (§1 concept image 이야기의 회수 지점)
- ★ 사상(구조) vs 행렬(표현) 구분은 §7의 선형 사상 vs 행렬, 이 노트의 수학 vs 구현 이중성과 같은 패턴 — 노트 34 (야코비안은 흐르지 않는다)와 4고지 MatMul에서 세계가 합류
- ★ 5고지 예고 — 어텐션은 내적의 손자 (2026-08-30 브로 질문에서): LLM의 "고차원"은 대부분 벡터 길이(ℝ^4096의 점 — 이름 없는 특성 축)이지 축 개수가 아니라, 실전 텐서는 3~5D뿐 — 폭발하는 건 순열이 아니라 **선형 결합의 자유도**. 어텐션의 `QK^T`는 내적의 행렬판("질문 벡터와의 정렬도" 측정)이고 정렬도대로 토큰을 가중 결합 — **"질문이 조합을 고른다"의 LLM 버전** (고르는 주체가 사람이냐 학습된 가중치냐의 차이). 참고 (같은 질문): 특성 축은 **무명 좌표**라 단독 축 교환은 새 관점을 주지 않음 (라벨 있는 NCHW 축의 교환만 관점 획득) — 다만 "모든 가중치의 행/열을 함께 바꾸는 동시 순열"은 네트워크를 같은 함수로 유지하는 **순열 대칭** (등가 최적해의 원천)
