### #5. ★ 신경망 미분 = "해석적 미분 + 자동 조립" (수치 미분 아님!)

- **출처**: step04 랍업 직전 브로 질문 (2026-07-24)
- **브로 혼동 포인트**: *"신경망이 '해석적 미분'과 '수치적 미분'이 결합된 형태 같기도?"*
- **답**: ❌ 수치 미분은 전혀 관여 안 함. 역전파는 **"해석적 미분 공식(사람이 유도) + chain rule 자동 조립(컴퓨터)"** 의 결합.
  - 각 연산(행렬곱, ReLU 등)의 미분 공식은 **사람이 미리 손으로 유도해서 코드에 박아둠** (해석적)
  - 역전파는 이 공식들을 chain rule로 **자동 연결** (자동성)
  - → 수치 미분의 근사 오차 없이, 해석적 정확도 + 자동성 둘 다 가짐
- **관련**: 행렬곱 미분은 **야코비안(Jacobian)** 으로 표현. `y = Wx` → `dy/dx = W^T` 등
- **키워드**: `#역전파` `#해석적미분` `#chain-rule자동조립` `#야코비안` `#Jacobian` `#행렬미분` `#W전치` `#autodiff리버스모드`
- **회수 조건**: 
  - step07+ 역전파 구현 시 (각 연산의 backward 공식이 해석적임을 코드로 체감)
  - step33 "행렬의 미분 이론" (야코비안 본격 등장)
  - step35 "행렬의 미분 구현 (MatMul)" (행렬곱 미분 공식 직접 다룸)

### #6. ★ 계산 그래프(DAG) 자료구조 vs Variable/Function "흡수" — 프레임워크 설계 철학

  3. ★ DAG가 Variable/Function에 **흡수**된 거 불편 → 자료구조적 측면 명확히 분리 불가?

- **핵심: 3가지 autograd 패러다임 비교** (이 탐구의 중심):

  | 프레임워크 | 방식 | 철학 | DAG 위치 |

  브로 혼란: *"만들어진 계산 그래프에 지속적으로 신규 입력값을 넣고 만들어진 그래프를 타고 계산이 돌아야 하는 것 아닌가? 현재 코드만 봤을 때는 학습이 어떻게 돌아가는지 전혀 모르겠다."*
  → ★★ **이 혼란 자체가 "Define-and-Run을 상상했다"는 증거**:
  - "만들어진 그래프에 신규 입력 feed" = **TF 1.x 방식** (placeholder/feed_dict)
  - Define-by-Run은 정반대: **매 입력마다 새 그래프 생성** (재사용 안 함)

- **★ Define-by-Run ↔ FP (함수형) 연결** (브로 통찰: "매번 재생성이 FP 스럽기도?"):
  - Define-by-Run: 매번 새 Variable/그래프 = **불변성 (immutability)** = FP 핵심
  - `pipe(x, square, exp, square)` (우리가 step09에서 만든) = Define-by-Run의 데이터 흐름 그대로 시각화
  - "고정된 그래프 재사용"이 아니라 "데이터가 함수를 통과하는 일회성 흐름" — FP와 같은 결
  - 반대급부: Define-and-Run은 그래프를 "객체"로 정의/재사용 → **명령형/OOP적** (상태ful)
  - → #14 (전역 fill_grad = JAX 스타일)와 step09 pipe가 같은 FP 철학의 다른 발현
- **★ 현재 코드에 학습이 안 보이는 이유** (브로 혼란의 구조적 원인):
  현재(step09)는 학습의 절반(forward + backward)만 구축. 나머지 절반은 앞으로:
  | 학습 단계 | 현재? | step |
  |---|---|---|
  | 1. 데이터 가져오기 | ❌ | step42+ (Dataset) |
  | 2. forward (그래프 구축 + 값) | ✅ | 지금 |
  | 3. loss 계산 | ❌ | step47 |
  | 4. backward (gradient) | ✅ | 지금 (fill_grad) |
  | 5. ★ 가중치 갱신 (경사하강법) | ❌ | **step28** (개념), step47 (루프 통합) |
  → 밑시딥 1권 `W -= lr * dW` 단계가 step28까지 안 나옴. 그래서 "학습이 안 보임" 정상.
- **★ 가중치 ↔ 계산 그래프 매핑 혼란** (브로 2차 질문, 2026-07-29):
  브로: *"가중치가 함수 부분에 위치? 그래디언트는 유지되어야 하는 값 아닌가? 가중치와 그래디언트를 계산 그래프와 어떻게 매핑?"*
  → ★★ 핵심 통찰 3가지로 머리 꼬임 해소:
  1. **현재 코드엔 가중치 없음** — Square/Exp는 순수 수학 함수 (가중치 0개).
     가중치는 **step49 (Layer/Affine)** 에서 등장. 그 전(step01~48)은 autograd 메커니즘 자체 구축 단계.
  2. **가중치 ≠ 그래디언트 유지 여부** (브로 혼동의 핵심):
     | 대상 | 유지? | 언제? |
     |---|---|---|
     | 가중치 `W.data` | ✅ 유지 (누적 갱신) | 학습 대상 — 매 반복 조금씩 갱신 |
     | 그래디언트 `W.grad` | ❌ 매번 새로 계산 | 이번 입력에 대한 방향, 재사용 안 함 |
     → 브로 "그래디언트 유지?" 혼동은 사실 **가중치 유지**와 바뀐 것.
  3. **★ 가중치도 Variable** — 입력 `x`와 같은 타입! 매핑:
     | 대상 | 그래프 위치 | 학습 대상? | 유지? |
     |---|---|---|---|
     | 입력 `x` | Variable (원점, creator=None) | ❌ | ❌ 매번 새 데이터 |
     | **가중치 `W`** | **Variable (원점, creator=None)** | **✅** | **✅ 누적 갱신** |
     | 중간 `y`, `loss` | Variable (creator 있음) | ❌ | ❌ 일회용 |
     → 가중치와 입력이 **같은 Variable 타입**이며 둘 다 그래프 원점.
     역전파가 원점들에 grad 채워주고, 그중 **가중치 것만** 갱신. 이게 Define-by-Run의 가중치 처리 방식.
  - cf. 밑시딥 1권 `Affine` 계층: 가중치가 클래스 속성으로 있었음 (`self.W`).
    DeZero는 이를 Variable로 일반화 — 가중치도 그래프의 일등 시민(first-class citizen).
  - 가중치 본격 등장 타임라인:
    step35 (MatMul, 행렬곱 시작) → step49 (Layer, Affine 구현) → step47 (학습 루프)
- **★ 브로 자가 도달 통찰 3종** (2026-07-29, step09 코드만 보고 유추 — Define-by-Run 본질 직관 파악):
  질문: *"가중치 객체 로컬 변수에 저장 재사용 → 파라미터 유지? 객체 참조 순회하며 갱신 공식 → 끝?
         그래디언트는 그 순간 것만 의미, 보존 의미 없다?"*
  → ★★★ 세 가지 전부 정확. Define-by-Run의 본질을 코드 구현 전에 구조적 이해에 도달:
  1. **가중치 객체 재사용**: 그래프는 매번 새로, 가중치 W는 그래프 밖에서 유지.
     `W = Variable(...)` 외부에서 만들고, 매 반복 `Affine(W)`로 같은 W 참조.
  2. **Optimizer 순회 패턴** (브로 통찰 = step49/47 구조 정확히 예측):
     가중치 Variable들의 참조 리스트를 가지고 `for p in params: p.data -= lr * p.grad`.
     "참조 가지니 순회하면 끝" — 이게 Optimizer.update()의 전부.
  3. **★★ 그래디언트의 순간성** (가장 깊은 통찰):
     그래디언트 = "현재 W + 현재 x에서의 loss 기울기".
     W 갱신/x 변경 → 이전 그래디언트는 의미 없음 → 매 backward마다 새로 계산, 보존 안 함.
     비유: 내비게이션 "지금 우회전" — 100m 가면 쓸모없음. 가중치는 현재 위치(유지), 그래디언트는 순간 방향.
  - cf. 밑시딥 1권 Affine: 가중치가 클래스 속성. DeZero는 Variable로 일반화.
    브로가 밑시딥 1권 경험 + Define-by-Run 학습으로 이 3종을 자가 도달한 것은 회수 시 핵심 자료.
- **★ "매번 그래프 새로 만드는 비용이 껌?" — 브로 통찰의 정확한 뉘앙스** (2026-07-29):
  브로: *"순전파는 수많은 입력 데이터 수만큼 이루어질 텐데, 매번 계산 그래프 새로 만들 거라고 생각 못 했다.
         파라미터 행렬 계산에 비하면 그래프 구축은 껌인가?"*
  → ★★ "껌"은 **조건부로 맞음** (두 층위):
  - **층위 A — 작은 모델**: 그래프 구축 비용 무시 못 함. 실제 병목.
    행렬곱(NumPy/CUDA) μs~ms vs Python 객체 생성/그래프 구축 같은 μs~ms 오더.
    작은 모델(MNIST MLP)에선 그래프가 오히려 5배 비쌀 수도. PyTorch 프로파일링서 "Python 오버헤드" 눈에 띄는 병목.
  - **층위 B — 큰 모델 + GPU**: 그래프 비용 무시 가능 ("껌" 맞음).
    행렬곱 100ms (수십억 파라미터) vs 그래프 구축 1ms → 1% 미만.
  - → 브로 통찰은 **극단적 상황(큰 모델)에서 맞음**. 작은 모델에선 틀림. 정확한 뉘앙스.
- **★ 왜 비용 감수하고 Define-by-Run 택했나 — "유연성 > 비용" 트레이드오프**:
  | 관점 | Define-and-Run (TF 1.x) | Define-by-Run (PyTorch) |
  |---|---|---|
  | 그래프 구축 | 1회 (컴파일) | 매번 (런타임) |
  | 비용 | 낮음 | 높음 (Python 오버헤드) |
  | 유연성 | 낮음 (고정 그래프) | ★★ 높음 (동적 — if/for 자유) |
  | 디버깅 | 어려움 (추상) | ★ 쉬움 (일반 Python) |
  → Define-by-Run은 **그래프 구축 비용을 감수하고 유연성/사용성 택함**.
  특히 가변 길이 입력(RNN, 트랜스포머 가변 시퀀스)은 그래프가 매 입력마다 달라져야 함.
- **★ 최신 트렌드 — "둘 다 잡기" (torch.compile, jax.jit)**:
  비용이 무시 못 될 정도라 컴파일 최적화가 가치 있음이 증명:
  - `torch.compile` (PyTorch 2.0+): Define-by-Run 코드 → 첫 실행 시 그래프 추적 → 컴파일 → 두 번째부턴 Define-and-Run처럼 빠르게
  - `jax.jit`: 함수형 코드 → JIT 컴파일 → 그래프 재사용
  → "매번 새로 만드는 비용"을 줄이면서 Define-by-Run 유연성 유지하는 하이브리드.
  브로 "껌?" 질문이 이 최신 트렌드 존재 이유를 정당화 — 비용이 진짜라서 최적화 가치 있음.
- **브로 원인 회고**: *"계산 그래프가 큰 자료구조처럼 보였다"*
  → ★ 이게 Define-and-Run 직관 (TF 1.x `tf.Graph` 영속 객체 이미지).
  Define-by-Run은 그래프가 "실행의 부산물"이라 영속적이지 않음. 브로 오해 출처 정확히 짚음.
- **★ DeZero의 목적과 범위 — torch.compile 급 최적화는 안 구현** (브로 통찰, 2026-07-29):
  브로: *"DeZero는 학습 목적이라 torch.compile 같은 건 안 구현? 이해 목적이니?"*
  → ★ 정확함. DeZero의 목적 = **"autograd가 어떻게 작동하는가" 밑바닥부터 이해** (교육용).
  | 목적 | DeZero | torch.compile 급 |
  |---|---|---|
  | 학습 (gradient + 가중치 갱신) | ✅ | — |
  | autograd 메커니즘 이해 | ✅ (핵심) | — |
  | 성능 최적화 (그래프 컴파일) | ❌ | PyTorch 2.0+ 실무 기술 |
  → 책 60 step 전체가 "이해"에 집중. torch.compile은 "이미 이해한 뒤 실무에서 쓰는 기술"이라 범위 밖.
  cf. rezero엔 MLX 백엔드 후보(Issue 1)가 "성능" 쪽 씨앗이긴 하나, 이것도 "이해 확장" 차원.
- **★ Define-by-Run → Define-and-Run 전환은 사실상 재설계** (브로 직감, 2026-07-29):
  브로: *"Define-by-Run을 Define-and-Run으로 바꾸는 건 쉽지 않을 것 같다"*

    반대 방향(Define-by-Run → Define-and-Run)도 동등하게 어려움.
  - cf. torch.compile은 "전환"이 아니라 "첫 실행 추적 + 컴파일" 하이브리드라 가능한 것.

### #7. Define-by-Run의 역사 — Chainer에서 PyTorch까지 (프레임워크 계보)

- **출처**: step31 랩업 중 브로 질문 (2026-08-20) — *"DeZero가 뭔가 모양새가 체이너와 비슷한가봐?"* + *"Chainer는 몇 년 전에 사망(?)했잖아?"*

- **핵심**:

  - **"Define-by-Run"이라는 용어 자체가 Chainer(2015) 발명** — 동적 계산 그래프 최초 구현

  - 우리 레포 tests/가 레퍼런스 비교 상대로 PyTorch가 아니라 **Chainer**를 쓰는 것 (Known Gotcha 1)도 혈연의 증거
  - 확장 주제: double backprop 용어도 Chainer 문서 유래 / TF 1.x→2.x의 Define-by-Run 전환 / 후보 #6 (autograd 패러다임 비교)와 자연 연결

### #10. ★★ "야코비안은 흐르지 않는다" — VJP와 autograd의 실체 (4고지 진입 전 개념 정리)

- **출처**: step34 랩업 중 브로 질문 (2026-08-24) — *"실제로 아직 야코비안스러운 게
  흐르는 건 아니잖아? 근데 element-wise 결과와 우연히 같은 결과를 내는 상황?"* /
  *"4고지 이상에서는 실제 backward 시에 야코비안이 실제 흐르게 되는 게 맞고?"*
  (+ 브로 요청: "머리가 꽤 혼동하는듯 — 4고지 진입 시점에 다시 생각해보기로")
- **교정된 관념** (질문 1은 정확, 질문 2는 절반만 맞음):
  - 3고지 (현재): `df(x) ⊙ upstream` — 대각만 압축 전송하는 **희소 야코비안** 관점
    (비대각 0성분은 계산 안 함). 야코비안 행렬은 코드가 존재 자체를 인식 못 함 —
    element-wise라는 조건에서만 수학과 일치 (조건부 필연)
  - 4고지+: backward 공식이 `gy·Bᵀ` 같은 **전치행렬 곱 = 진짜 VJP**를 직접 계산.
    그러나 ★ **야코비안 행렬 자체는 여전히 만들어지거나 흐르지 않음** —
    흐르는 건 언제나 gradient (VJP의 결과)뿐
  - "야코비안이 흐른다"는 autograd의 유명한 오해 — 모든 backward는 "국소 VJP"
    (함수마다 유도된 곱셈 공식)
- **살펴볼 것**: 4고지 MatMul backward 공식이 어떻게 Jᵀ·gy 형태가 되는지 직접 유도,
  gradient check로 검증, 텐서 shape 맞추기 게임(구현)과 기저 변환(수학)의 분리 —
  브로 머리에서 명료해질 때까지
- ★ **VJP vs JVP 쌍둥이 구분** (브로 질문에서 정리, 2026-08-24):
  JVP = Jacobian-Vector Product = **J·v** (순방향 모드) /
  VJP = Vector-Jacobian Product = **vᵀ·J** (역방향 모드 = backprop).
  영어 어순 = 곱셈 순서. JAX가 jax.vjp/jax.jvp API로 둘 다 제공하는 공식 용어.
  ★ 우리 노트 일부에 "야코비안-벡터 곱(VJP)"라 쓴 곳 — 한글 풀이(JVP 것)와
  약자(VJP)가 뒤집힌 표기. 결론 "역전파 = VJP"는 맞음.
- ★ **브로 직관 확정** (같은 날): "gradient가 흐른다는 건 신경망 전체 흐름상에서,
  야코비안이 등장하는 건 중간 계산 과정에서 살짝" — ✅ 정확.
  전체 chain rule은 J_L···J_1 연쇄곱이지만 실제 계산은 오른쪽부터 한 단계씩
  (g_i = g_{i+1}ᵀ·J_{i+1} = backward 한 번) — 흐르는 건 항상 벡터, 야코비안은
  각 교차로의 변환기 (명시적으로 만들어지지도 않음). fill_grad의 worklist 순회에서
  각 f의 df(x) * upstream이 바로 그 국소 VJP.
- ★ **분모 표기 관례** (브로 질문, 같은 날): 3고지까지 미분 대상(분모)은 언제나
  **개별 스칼라 변수** (dy/dx, ∂z/∂x·∂z/∂y, step34도 "x_i 각각 200개" — B 루프
  버전이 증명). "분모에 벡터 통째로" (∂L/∂w, w∈Rⁿ)는 4고지 관례 — 실체는
  **모든 성분 편미분을 w와 같은 shape으로 모은 묶음**의 축약 (엄밀한 분수 아님).
  이 "모아서 같은 shape"이 4고지 shape 맞추기 게임의 정체.
  + 표기 위상 (추가 질문에서): 수학의 정식 도구는 **nabla** (∇f — "벡터 분모"의
  공식화). 행렬미적분학은 ∂y/∂x를 진짜 정의로 다루나 **numerator/denominator
  layout 두 파벌**이 갈려 전치가 뒤집히는 악명 — 딥러닝은 denominator layout
  (gradient를 가중치와 같은 shape)이 사실상 표준. 4고지 공식 유도 시 전치 위치로 재회 예정.
