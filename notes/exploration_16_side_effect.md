## 1. 문제: 번역어가 원어보다 더 나쁘게 느껴진다

브로가 step08 학습 중 `assert funcs.pop()` 예시를 보고 "부작용"이란 단어에 강한 거슬림을 느낌.
그 불편감의 본질은 **원어와 번역어의 감정색(mood) 불일치**.

| | 영어 **side effect** | 한국어 **"부작용"** |
|---|---|---|
| 감정색 | **중립적** (기술 용어, 가치 판단 없음) | **부정적** ("원치 않는 나쁜 결과") |
| 사전 정의 핵심 | secondary effect (부차적 효과) | "본래 목적 외에 달리 미치는 **나쁜** 영향" ★ |
| 연상 | 프로그램 동작의 한 측면 | 약물 부작용, 정책 부작용 |
| 기대치 | 있을 수 있고, 있어야 하는 것도 있음 | 없어야 하는 것 |

★ 핵심 왜곡: **한국어 "부작용"의 사전 정의에 "나쁜"이 박혀 있다.**
반면 CS에서의 side effect는 "undesirable(바람직하지 않은)"을 **빼고** 쓴다.
→ 번역어가 원어보다 **부정적 뉘앙스를 더 강하게** 주입.

**그래서 브로가 느끼는 "잘못된 것 아닌가?" 직감의 출처**:
"부작용"을 들으면 뇌가 **본능적으로 "이건 문제야"** 라고 반응하지만, 원어엔 그 색채가 없으니
— **번역어가 원어보다 더 나쁘게 느껴지는** 인지적 왜곡이 발생.

> 💡 브로 발언: *"머리에 `사이드 이펙트 == 부작용 == 나쁜 것`으로 박혀있는 듯"*
> → 이게 바로 [Sapir-Whorf 가설](https://en.wikipedia.org/wiki/Linguistic_relativity)의 사례.
> "언어가 사고를 형성한다" — 우리가 쓰는 단어가 우리가 생각하는 방식을 제한한다.
> 번역어가 부정적 뉘앙스를 주입하면, 개념 자체를 부정적으로만 인지하게 됨.

## 2. side effect의 중립적 정의 (CS 공식)

**관측 가능한 외부 효과 (observable side effect)** — 함수가 "입력 → 출력" 매핑 외에
세상(외부 상태)에 미치는 모든 영향. 가치 중립.

공식 정의 ([Wikipedia: Pure function](https://en.wikipedia.org/wiki/Pure_function),
[freeCodeCamp](https://www.freecodecamp.org/news/pure-function-vs-impure-function/) 참조):

> A function is said to have a **side effect** if it modifies some state outside its scope
> or has an observable interaction with the outside world.

대표적 외부 효과들:
- **상태 변경 (mutation)**: 전역 변수, 가변 데이터 구조, 객체 속성 수정
- **I/O**: 화면 출력(`print`), 파일 읽기/쓰기, 네트워크, DB
- **외부 입력 읽기**: 키보드, 센서, 클럭(`time.now()`)
- **예외 발생**: `raise` (정상 반환 외의 제어 흐름)
- **메모리 할당/해제**: (추상화 단계에 따라 관측 가능으로 치기도 함)

```python
# 순수 함수 (pure function) — 외부 효과 없음. 같은 입력 → 항상 같은 출력.
def add(a, b):
    return a + b

# 외부 효과가 있는 함수들
counter = 0
def increment():          # ① 상태 변경
    global counter
    counter += 1

def greet(name):          # ② I/O (출력)
    print(f"hi {name}")

def log_to_file(x):       # ③ I/O (파일 쓰기)
    with open("log.txt", "a") as f:
        f.write(str(x))
```

★ 핵심 — **외부 효과는 "나쁜 것"이 아니라 "선택지"**:
- 함수형 패러다임: 외부 효과를 **최소화/격리** (순수 함수로 구성 → 테스트·병렬화·예측성 향상)
- 명령형/OOP 패러다임: 외부 효과를 **적극 활용** (상태 변경이 곧 프로그램의 본질)
- 현실: 아무 외부 효과도 없는 프로그램은 계산만 하고 아무것도 안 함 (I/O 없으면 무용)
  → "외부 효과를 없애라"가 아니라 "통제 가능하게 관리하라"가 정답.

> 💡 **추상화 단계 주의** ([John D. Cook](https://www.johndc\ook.com/blog/2010/05/18/pure-functions-have-side-effects/)):
> 엄밀히 모든 함수는 CPU 시간·메모리를 소모하지만, 이건 관측 대상이 아님.
> "순수"는 **특정 추상화 단계에서** 관측 가능한 효과가 없다는 뜻 — 절대적 기준 아님.

## 3. 순수 함수 vs 외부 효과 함수 — 패러다임의 두 축

| | 순수 함수 (pure) | 외부 효과 함수 (impure) |
|---|---|---|
| 정의 | 같은 입력 → 항상 같은 출력, 외부 상태 안 건드림 | 외부 상태를 읽거나 바꿈 |
| 예 | `math.sqrt`, `add(a,b)` | `print`, `random.random`, `time.now` |
| 테스트 | 쉬움 (입출력만 보면 됨) | 어려움 (외부 상태 셋업/검증 필요) |
| 병렬화 | 안전 (공유 상태 없음) | 위험 (레이스 컨디션) |
| 캐싱 | 가능 (같은 입력=같은 결과) | 불가 (결과가 외부에 의존) |
| 프로그램 역할 | 계산 (computation) | 효과 (effect) — I/O, 상태 변화 |

**함수형 프로그래밍의 핵심 통찰**:
- 계산(computation)과 효과(effect)를 **분리**하면 추론이 쉬워진다
- 순수한 코어(계산) + 얇은 효과 셸(I/O) 구조가 이상적
- Haskell의 `IO` 모나드가 이 분리를 언어 수준에서 강제하는 극단적 예

→ "외부 효과 = 악"이 아니라 **"외부 효과를 순수한 부분과 분리하면 좋다"**.

## 4. 최적화와 외부 효과의 충돌 (assert, C UB, Java 사례)

이게 브로가 "다른 언어에서도 봤다"고 한 부분의 본질.
**컴파일러/인터프리터의 최적화가 외부 효과를 보존하지 않으면 프로그램이 망가진다.**

### 사례 1: Python `assert` + `-O` 모드 (★ step08 직접 계기)

```python
funcs = [1, 2, 3]
assert funcs.pop() == 3
```

- 일반 모드: `pop()` 실행 → `funcs = [1, 2]` (조건 평가하느라 외부 효과 발생)
- `-O` 모드: assert 통째로 사라짐 → `funcs = [1, 2, 3]` ★ **외부 효과 자체가 안 일어남**

상세: [debugging.md](./debugging.md) 항목 1.

### 사례 2: C 언어 미정의 동작 (Undefined Behavior)

```c
int x = 0;
x = x++ + 1;   // UB — x의 최종값이 정의되지 않음
```

- `x++`는 **외부 효과(x 증가)**, `+1`과 대입 순서가 정의 안 됨
- 컴파일러는 UB를 가정하고 **외부 효과를 마음대로 재배치/제거** 가능
- → 최적화 수준(`-O2`, `-O3`)에 따라 결과가 달라지는 재앙
- clang/gcc가 `-Wall`로 경고는 주지만, 외부 효과 순서에 대한 프로그래머 가정을 깨뜨림

### 사례 3: Java — `assert` 기본 비활성화

- Java의 `assert`는 JVM 실행 시 **기본적으로 꺼져 있음** (`-ea` 플래그로 켜야)
- Python과 달리 "개발 중에만 켜는 게 기본값"
- 같은 원리: assert 조건에 외부 효과 넣으면 프로덕션(기본 off)에서 사라짐

### 공통 교훈

> **외부 효과(side effect)가 있는 표현식은 최적화 대상이 될 수 없다.**
> 컴파일러/인터프리터는 "외부 효과 없는 코드"만 자유롭게 재배치/제거할 수 있다.
> 따라서 최적화가 개입하는 자리(`assert`, UB, 매크로, lazy eval)엔 **순수 표현식만** 둘 것.

이게 "부작용"이 아니라 "외부 효과"라 부르는 게 맞는 이유:
**"외부 효과"**는 "관측 가능한 상태 변화"라는 중립 사실만 말하지만,
**"부작용"**은 "나쁜 것" 뉘앙스가 있어서 "왜 최적화가 깨지는지" 본질(효과 보존 의무)을 가림.

## 5. 대안 번역과 인지 재세팅

브로가 "머리에 박혀있다"고 한 인지 박제를 풀려면 — **새 번역어로 재프로그래밍**.

웹 검색([함수형 프로그래밍 입문 역서](https://hjaem.info/articles/kr_3_1),
[가치관제작소](https://valuefactory.tistory.com/733) 등)에서 검증된 대안 번역들:

| 번역 | 장점 | 단점 | 추천도 |
|---|---|---|---|
| **부수 효과** | "side(부수)" + "effect(효과)" 직역, 중립적, 이미 학술 사용 있음 | "부수"가 약간 생경 | ★★★★★ |
| **외부 효과** | "외부 상태에 미치는 효과" 의미 정확, 본문("외부 상태")과 일치 | "side"를 "외부"로 의역 | ★★★★ |
| **종속 효과** | 효과의 종속성 강조 | 학술 사용 거의 없음 | ★★ |
| 부작용 (기존) | — | 부정 뉘앙스, 원어 왜곡 | ★ (회피) |

**이 노트의 정책**: 앞으로 `side effect`는 **"외부 효과"** 로 표기 (본문 맥락과 가장 일치).
"부작용"은 원어 side effect가 부정적 문맥에서 쓰일 때만(undesirable side effect) 한정.

> 💡 **인지 재세팅 실전**:
> "이 코드엔 부작용이 있다" (× 나쁜 코드네?)
> "이 코드엔 외부 효과가 있다" (○ 아, 외부 상태를 건드리는구나 — 중립적 사실)
> → 같은 코드, 같은 사실이지만 **느낌이 다르다**. 이게 번역의 힘.

## 6. 왜 "부작용" 번역이 굳어졌나 — 추정

정확한 어원 추적은 어려우나 합리적 추정:

1. **초기 번역의 경로 의존성** — 80~90년대 CS 용어 도입 시, side effect를 직역하면
   "부(副)+작용"이 가장 자연스러웠을 것. 약물 "부작용"과 같은 한자어 재사용.
2. **번역어의 관성** — 한번 굳어진 학술 용어는 바꾸기 어려움. 나무위키, 교재, 강의 모두
   "부작용"을 쓰니 새 입문자가 계속 같은 인지 박제를 물려받음.
3. **의학 용어와의 충돌** — 영어도 의학에서 "side effect"를 "undesirable" 뉘앙스로 쓰긴 하나,
   CS에선 명백히 중립으로 재정의. 한국어는 이 **재정의가 번역어에 반영 안 됨**.
4. **"부수 효과"가 더 늦게 제안됨** — 이미 "부작용"이 표준처럼 자리잡은 후라 전환 비용 큼.

→ 번역학 일반적 교훈: **기술 용어 번역 시 원어의 감정색까지 옮겨야** (여기선 중립성 보존).
   부정적 뉘앙스를 덧칠하는 번역은 학습자 인지를 영구 왜곡.

이건 [exploration_14 "미분(微分)" 번역 비판](./exploration_14_derivative_terminology.md)과 같은 결:
- 미분(微分): 한자 "작게 쪼갠다" → 영어 differentiation "차이를 본다"의 본질 은폐
- 부작용: 한자 "나쁜 영향" → 영어 side effect "부차적 효과"의 중립성 은폐
- 공통점: **초기 번역어가 굳어지면서 원어의 정확한 의미가 가려짐**

### 6.1 개인 인지 버전 — "왜 자동으로 부작용이 나오나" (브로 불편감의 뇌 과학)

§6는 "사회적 번역 관성"을 다뤘다면, 여기는 그 **개인 인지 버전**.
브로가 "부수 효과를 본 적 있는데 왜 자동으로 부작용이 나오지?" 라고 물은 것의 답.

**3가지 메커니즘의 합작**:

#### ① 빈도 효과 (Frequency Effect) — 가장 큰 원인
- "부작용" = 일상어 (약물·정책 부작용 등) → **태어나서 수천 번 노출**
- "부수 효과" = 전문 용어 → **한두 번 접한 정도**
- 뇌는 자주 노출된 단어의 경로를 더 빠르고 강하게 깔아둠. **고속도로 vs 시골길.**
- "본 적 있다"는 접속만 됐을 뿐, 빈도 우위는 여전히 "부작용" 쪽.

#### ② 인식(recognition) vs 생성(production)의 분리 ★ — 브로 경험의 핵심
이게 제일 중요한 통찰. **"아는 것"과 "자동으로 튀어나오는 것"은 다른 뇌 과정**이다.

| 과정 | 설명 | 브로 경험 |
|---|---|---|
| **인식 (recognition)** | 외부 자극을 보고 의미를 앎 | "부수 효과"를 보면 "아 맞다" 함 (O) |
| **생성 (production)** | 내부에서 자발적으로 단어를 산출 | 말하려니 "부작용"이 먼저 튀어나옴 (X) |

- 인식은 **문맥 단서**가 도와주지만, 생성은 **빈도·연결 강도**가 지배
- → 외국어 학습의 "읽으면 이해되는데 말은 안 나온다"와 **동일한 원리**
- "안다" ≠ "자동으로 쓴다". 재프로그래밍은 인식만으론 안 되고 **생성 경로**를 훈련해야 함.

#### ③ 활성화 확산 (Spreading Activation)
- `side effect` 자극 → 시맨틱 네트워크에서 **가장 강한 연결("부작용")이 먼저 불켜짐**
- "부수 효과"/"외부 효과"는 약한 연결 → **의식적 탐색**해야 도달 (느리고 힘듦)
- 강화 학습 관점: "부작용" 고속도로 vs "외부 효과" 새 길. 새 길이 이기려면 **반복 사용**뿐.

#### ★ 대칭 구조: 사회 ↔ 개인

| | 사회적 차원 (§6) | 개인 인지 차원 (§6.1) |
|---|---|---|
| 현상 | "부작용" 번역이 학계에 굳어짐 | "부작용"이 개인 어휘 접근에 자동 |
| 원리 | 경로 의존성 + 번역어 관성 | 빈도 + 인식/생성 분리 + 활성화 확산 |
| 결과 | 원어 중립성이 사회적 인지에서 가려짐 | 원어 중립성이 개인 인지에서 가려짐 |
| 해소 | 학계 전체의 용어 전환 (느림) | **개인의 반복 사용** (가능) |

→ 개인 차원이 사회 차원보다 **해소가 빠르다** — 의식적 반복으로 새 경로 강화 가능.
이 노트가 "재프로그래밍 훈련장" 역할: 앞으로 "외부 효과"를 계속 쓰면서 브로 뇌의 새 경로를 강화.

#### ★ 프로그래밍과의 연결
이건 강화 학습(RL) 그 자체다:
- "부작용" 경로 = **보상(이해됨)을 수천 번 받아 강화된 정책**
- "외부 효과" 경로 = **새 정책** — 처음엔 의식적 exploration 필요, 반복하면 exploitation으로 전환
- → 재프로그래밍 = 새 정책의 가치를 올려 무한대까지 쓰는 것. (step47 학습 루프의 어휘 버전)

## 7. DeZero/rezero에서의 외부 효과

이 탐구의 출처인 step08을 포함, rezero 구현에서 외부 효과가 등장하는 지점들:

| 위치 | 외부 효과 | 순수 vs 외부 |
|---|---|---|
| `Variable.__init__` (`self.data = data`) | 객체 상태 초기화 (mutation) | 외부 효과 |
| `Variable.grad` / `.creator` 할당 | 객체 속성 변경 | 외부 효과 |
| `Function.__call__` (`self.input = ...`) | 인스턴스 상태 저장 | 외부 효과 |
| `forward` / `apply` (순수 수학: `x**2`, `np.exp(x)`) | 없음 — 입력 → 출력 매핑 | **순수** ★ |
| `backward` / `derivative` (도함수 평가) | 없음 — 수학 계산 | **순수** ★ |
| 전역 `backward()` (그래프 순회 + grad 채우기) | Variable들에 grad 할당 | 외부 효과 |
| `print(...)` (데모 출력) | I/O | 외부 효과 |

★ 흥미로운 분리:
- **수학 코어** (apply/derivative): 순수 함수 — 같은 입력에 같은 출력, 부작용 없음.
  DeZero의 "역전파가 해석적 미분이다"는 게 이 순수성에서 옴.
- **프레임워크 셸** (Variable/Function 상태 관리, 그래프 순회): 외부 효과 투성이.
  Define-by-Run은 순전파 시점에 상태(creator 링크, input/output)를 기록하는 구조.

→ 함수형 패러다임 관점에서 보면, DeZero는 **"수학 코어(순수) + 상태 관리 셸(외부 효과)"** 구조.
이 분리 의식이 `derivative()`가 callable을 반환하는 rezero 변형(항목 13번)과도 통함 —
도함수를 순수한 함수 객체로 취급하려는 시도.

## 8. 핵심 요약

1. **"부작용"은 잘못된 번역** — 원어 side effect는 중립적 기술 용어인데, 한국어 "부작용"은
   "나쁜 영향" 부정 뉘앙스가 사전 정의에 박혀 있어 인지 왜곡.
2. **정확한 번역은 "외부 효과" 또는 "부수 효과"** — "함수가 외부 상태에 미치는 관측 가능한 영향".
3. **외부 효과는 중립적 선택지** — 함수형은 최소화, 명령형은 적극 활용. 어느 쪽이든 "악"이 아님.
4. **최적화와 외부 효과는 충돌** — assert(`-O`), C UB, Java assert 모두 같은 원리.
   외부 효과 있는 코드는 최적화 대상이 될 수 없다. "순수 표현식만 assert에" 교훈.
5. **번역이 인지를 지배** — "부작용=나쁘다" 박제는 번역어가 만든 인위적 인지.
   "외부 효과"로 재프로그래밍하면 원어의 중립성 회복.
6. **DeZero와의 연결** — 수학 코어(apply/derivative)는 순수, 프레임워크 셸은 외부 효과.
   역전파의 정확성이 수학 코어의 순수성에서 옴.
