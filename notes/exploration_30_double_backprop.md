## 1. 결론 먼저 — 3단 논법

step31 전체를 한 논리로 압축하면:

1. **미분 계산도 결국 계산이다** — 곱셈과 덧셈의 나열 (예: `gx = 2 * x * gy`)
2. **DeZero에서 계산은 실행만 하면 그래프로 남는다** — Define-by-Run (step07~09)
3. **남은 그래프는 또 미분할 수 있다** — 같은 backward를 한 번 더 부르면 된다

→ 따라서 2차, 3차, ... n차 미분이 **무한히** 가능해진다 (step34의 sin y', y'', y'''이
이 논리의 직접 산물). 필요한 변경은 단 하나: **역전파 내부의 계산을 Variable
연산으로 수행하는 것**.

## 2. 문제 제기 — 현재 구조의 "기억 상실"

2차 미분의 수학적 정의부터:

$$
\dfrac{d^2y}{dx^2} = \dfrac{d}{dx}\left(\dfrac{dy}{dx}\right)
$$

즉 **dy/dx를 다시 x로 미분**하라는 뜻. 그런데 현재 `fill_grad` 후의 `x.grad`는
ndarray다. ndarray에는:

- `creator`가 없다 → 이 값이 어떤 계산에서 나왔는지 **기록이 없다**
- 그래프가 없다 → 미분 대상인 "식"이 존재하지 않는다

`y = x²`을 미분하면 `x.grad = 2x`의 **값** (예: x=3일 때 6.0)이 남지만, 그 값이
`2·x`라는 **식**이었다는 사실은 사라진다. 값을 미분할 수는 없다 — **미분하려면
계산 과정(그래프)이 필요한데, 1차 미분을 하면서 그 그래프를 버렸기 때문**이다.

| | 값 (ndarray) | 식 (그래프) |
|---|---|---|
| 정체 | `6.0` | `2·x` |
| 미분 가능? | ❌ (상수, 기억 상실) | ✅ (d/dx = 2) |
| 재료 | 결과만 있음 | 계산 과정 전체 |

## 3. 핵심 통찰 — dy/dx는 값이 아니라 함수다

이 문제의 인식론적 뿌리. dy/dx = 2x를 "값"으로 보면 2차 미분은 불가능하고,
"**x의 함수**"로 보면 미분 대상이 된다:

$$
\dfrac{dy}{dx} = 2x \quad \Rightarrow \quad \dfrac{d}{dx}\left(\dfrac{dy}{dx}\right) = \dfrac{d(2x)}{dx} = 2
$$

그렇다면 "2x라는 함수"를 코드로 어떻게 표현할까? **계산 그래프로** — 그리고
그래프를 만드는 방법은 이미 알고 있다. 실행하면 된다 (Define-by-Run).

## 4. 해결책 — 역전파 내부를 Variable 연산으로

Square의 backward를 before/after로 비교하면 변경점이 명확해진다.

**[현재 — rezero v1]** (기억 상실 버전)

```python
class Square(Function):
    def backward(self, gy):
        x = self.inputs[0].data   # ndarray를 꺼냄
        gx = 2 * x * gy           # ndarray 연산 — 흔적이 안 남는다. 끝!
        return gx
```

**[개선 — step32에서 구현할 그림]** (그래프 남기는 버전)

```python
class Square(Function):
    def backward(self, gy):
        x = self.inputs[0]        # ★ Variable 그대로!
        gx = 2 * x * gy           # ★ Variable 연산 → Mul 노드가 생기고
        return gx                 #   gx는 creator를 갖는 Variable = "2x 식"
```

차이는 딱 두 곳: `.data`를 꺼내지 않는 것, 그래서 곱셈이 Variable끼리 일어나는 것.
이러면 backward 한 번이 **자기 자신의 계산 그래프를 구축하는 순전파**가 된다.

## 5. y = x² 풀코스 — 2층 그래프의 전체 그림

책의 확장 다이어그램(30단계 그림 + 역전파 층)을 ASCII로 옮기면:

```
   [2층 — 미분 계산의 그래프]        ← 1차 역전파가 "만든" 새 그래프

        gy = Variable(1) ──────┐
        (리프: 상수도 노드)     │
                               ▼
        x ──────────────────→ Mul ──→ ... ──→ gx = 2x
        (1층 리프를 재사용!)                        │
                                                  │ gx.backward()
                                                  ▼
                                             d(2x)/dx = 2  ★ 2차 미분

   [1층 — 원래 함수의 그래프]

        x ───→ Square ───→ y
```

읽는 순서:

1. **순전파**: 1층 그래프 구축 (x → Square → y)
2. **1차 역전파** (`create_graph=True`): 1층을 거꾸로 흐르며 2층 그래프를 쌓는다.
   gy는 `Variable(1)` — 상수조차 그래프의 리프 노드가 된다. x는 1층 리프를 그대로
   재사용 (같은 Variable 객체 — Define-by-Run이 보장하는 연결)
3. **2차 역전파**: `gx`는 그래프를 가진 Variable이므로, gx에 대해 다시 역전파를
   흘리면 2층 그래프를 타고 내려가 **x에 2가 도착한다** = f''(x)

핵심 대칭: 순전파의 출력 y가 그래프를 가지듯, **역전파의 출력 gx도 그래프를 가진다.**

## 6. 머리가 꼬이는 3지점 해부

브로가 느낀 꼬임은 이론이 어려워서가 아니라, 익숙한 구분이 흔들리기 때문이다.

**꼬임 A: "backward가 forward를 만든다?"**
역전파를 "그래프를 거꾸로 흐르는 특별한 작업"으로 이미지하면 꼬인다. 실상
backward는 그냥 **호출되는 함수**고, 함수 본문에서 Variable 연산을 하면
Define-by-Run 규칙에 의해 그래프가 자동으로 쌓이는 것뿐. 새로운 마법이 아니라
**기존 규칙을 backward 자신에게도 그대로 적용**한 것이다.

**꼬임 B: "gy(시작 기울기)는 뭐지?"**
역전파의 출발점. 그동안 `np.ones_like(x.data)`로 만드는 무명의 상수 취급이었는데,
그래프를 남기는 세계에서는 이것도 Variable(리프)이어야 한다. **상수 1도
그래프의 잎**이라는 전환 — 2층 그래프의 가장 왼쪽 노드다.

**꼬임 C: "그래프가 2층으로 쌓인다?"**
맞고, 그대로 받아들이면 된다. 아래층 = 원래 함수, 위층 = 미분 계산. 2차 역전파는
위층에서 시작해 아래층 리프(x)까지 내려가는 화살표를 만든다. 참고로 이 구조는
**필요한 만큼 위로 계속 쌓인다** — 3차 미분은 2차 역전파의 그래프(3층)를 또
남기면 된다 (step34의 sin 삼각함수 미분 사이클이 이것을 시각화한다).

## 7. Define-by-Run의 자기 참조 — 이 설계가 아름다운 이유

step07~09에서 세운 원칙: **"실행하면 그래프가 생긴다"** (Define-by-Run의 본질).

double backprop은 이 원칙을 backward에게도 적용한다:

| | 실행 주체 | 실행 결과 | 그래프 |
|---|---|---|---|
| 순전파 | `__call__` | y | 1층 (원래 함수) |
| 역전파 (`create_graph=True`) | `backward` | gx | 2층 (미분 함수) |
| 역역전파 | `backward` | gxx | 3층 (2차 미분 함수) |

순전파/역전파의 비대칭이 사라지고 **"모든 실행은 그래프를 낳는다"라는 완전한
대칭**이 성립한다. 프레임워크에 특별한 "고차 미분 모드"를 추가하는 게 아니라,
기존 설계의 논리를 일관되게 밀어붙인 결과가 고차 미분 — 좋은 설계의 증표다.

## 8. 수학 좌표 — gradient / Jacobian / Hessian (용어 3형제)

이 노트의 주인공(2차 미분)은 수학 지도 위 어디에 있는가. 3형제를 헷갈리는 건
둘 다 "행렬 형태의 미분"처럼 보이기 때문인데, 구분 축은 따로 2개다 —
① 함수 출력이 스칼라냐 벡터냐, ② 몇 차 미분이냐.

| 함수 형태 | 1차 미분 | 2차 미분 |
|---|---|---|
| 스칼라 → 스칼라 (**책 지금 세계**) | f' (스칼라) | f'' (스칼라) |
| Rⁿ → R (**딥러닝 loss**) | **gradient** (벡터) | **Hessian** (n×n 행렬) |
| Rⁿ → Rᵐ (벡터 출력) | **Jacobian** (m×n 행렬) | (3차 텐서) |

- **Jacobian** = 벡터 함수의 1차 미분
- **Hessian** = 스칼라 함수의 2차 미분 = **gradient의 Jacobian**

### ★ Hessian은 "특수한 야코비안"이다 — 포함 관계와 고유 성질

질문: *"Hessian이 특수한 야코비안의 앨리어스였다는 소리니?"* — 방향은 맞고,
정확히는: **모든 Hessian은 야코비안이지만, 모든 야코비안이 Hessian은 아니다.**

단계별로 보자. f: Rⁿ → R (스칼라 함수, 딥러닝 loss)이라면 —

1. ∇f: Rⁿ → Rⁿ — gradient는 사실 **벡터 함수**다 (스칼라 함수의 1차 미분)
2. J(∇f) — 이 gradient의 야코비안이 바로 **Hessian**

즉 Hessian은 "야코비안을 **gradient에 적용한 특수 케이스**"에 붙은 전용 이름이다.
전용 이름이 필요한 이유도 있다 — 스칼라 함수의 2차 미분이라는 중요한 특수
상황이라는 점에 더해, **슈발츠 정리**(편미분이 연속이면 2차 편미분의 순서를
바꿔도 결과가 같음)에 의해 Hessian은 **대칭 행렬**(H_ij = H_ji)이 된다는 고유
성질이 따라온다. 일반 야코비안에는 없는 성질이다.

딥러닝으로 내려오면: loss는 Rⁿ→R 꼴이므로 — **역전파가 계산하는 게
gradient, double backprop이 계산할 수 있게 되는 게 Hessian**. 책의 스칼라
세계(dy/dx, d²y/dx²)는 이 일반론의 1변수 특수 케이스다.

사족: 사실 지금 역전파 내부에서도 Jacobian이 **암묵적으로** 돌아가고 있다 —
backward는 "야코비안을 명시적으로 만들지 않고 곱만 흘리는 것"(VJP)이라
메모리가 절약된다. 이 이야기는 텐서 미분(4고지)에서 재회한다.

## 9. 실무 좌표 — 적합성과 사용 빈도

- **빛나는 곳**: 뉴턴 방법의 f'' (step33에서 즉시 수확 — gx2 손유도 대체),
  물리 시뮬레이션의 곡률 (탐구 노트 29와 직결), 변분 추론·메타러닝처럼
  "gradient의 gradient"가 필요한 연구
- **과한 곳**: 일반 SGD 학습 — 2차 미분을 안 쓰는데 그래프까지 남기면
  메모리만 2배로 늘어난다

그래서 `create_graph`는 **옵션(기본 False)** 이 된다. step18의 `retain_grad`,
`no_grad`와 같은 철학의 연장선 — **기본은 버리고(lean), 필요할 때만 남긴다.**

### 사용 빈도의 진실 — 1차 압도적, 2차 간혹, 3차+ 사실상 없음

| 차수 | 실무 딥러닝에서 | 예시 |
|---|---|---|
| 1차 | **압도적** (사실상 전부) | SGD, Adam — 전부 gradient만 씀 |
| 2차 | 간혹 | 뉴턴식 최적화(소규모), 옵티컬 플로우의 Lucas-Kanade, 메타러닝 일부, "learning to learn by gradient descent"류 연구 (gradient가 입력이라 gradient의 gradient 필요) |
| 3차+ | 거의 없음 | 물리 시뮬레이션, 이론 연구 정도 |

이유는 **비용 폭증**. 2차 미분(Hessian)은 파라미터 N개면 N²개 값이라 수백만
파라미터 신경망에서는 저장 자체가 불가능하다 — 그래서 실무 2차 기법도 Hessian
전체가 아니라 "벡터 하나만 곱한 결과"(HVP)를 얻는 편법을 쓴다. 3차 이상은
그래프 층이 차수만큼 누적되니 메모리·계산이 계속 배가. 그리고 대부분의 학습
신호는 1차로 충분하다 — Adam 같은 적응적 1차 방법이 "2차 정보의 싸게 만든
근사" 역할을 어느 정도 대신해준다.

### ★ 능력 시연 ≠ 실무 빈도 (step34를 읽는 자세)

step34의 sin 반복 미분(y' → y'' → y''' 그래프) 데모는 "실무에서 이렇게 쓴다"가
아니라 **"프레임워크가 이런 것도 된다"는 능력 시연(capability demo)**이다.
Define-by-Run을 backward까지 일관되게 적용하면 n차 미분이 공짜로 따라온다는
**구조적 일반성의 증명**이지, 사용 빈도와는 무관하다 — 시속 200km 가능 광고 ≠
일상 주행이 200km. (미분할 때마다 sin→cos→-sin→-cos로 **순환하는 삼각함수의
성질**이 "3번 미분해도 의미가 드러나는" 보기라 책이 이 예를 골랐다.)

## 10. 역사 좌표 — "double backprop" 용어의 계보 (Chainer)

이 용어가 Chainer 계보에서 쓰이는 데엔 이유가 있다. **DeZero는 사실상
교육용 미니 Chainer**다:

- 저자 사이토 고키가 **PFN(Chainer 개발사) 출신** — `Variable`/`Function`
  네이밍을 그대로 계승
- **"Define-by-Run"이라는 용어 자체가 Chainer(2015)의 발명** — 동적 계산
  그래프를 이 이름으로 실현한 게 세계 최초
- Chainer는 2021~23년 개발 종료로 "사망"했지만, Define-by-Run은
  PyTorch(2017)로 계승되어 업계 표준이 됨 — **프레임워크는 죽어도
  패러다임은 승리한** 케이스
- 우리 레포 tests/가 DeZero의 레퍼런스 비교 상대로 PyTorch가 아니라
  **Chainer**를 쓰는 것(Gotcha 1)도 이 혈연의 증거

★ 계보 풀스토리(타임라인, PyTorch 계승, TF 2.x 전환 등)는 별도 탐구 후보로
크게 파기: [RESEARCH_QUEUE 후보 7번](./RESEARCH_QUEUE.md) 참고.

## 11. step32 미리보기 — 구현 편에서 실제로 바뀔 것

| 항목 | 현재 (rezero v1) | step32 이후 |
|---|---|---|
| `x.grad` 타입 | ndarray | Variable (그래프 소유) |
| gy 시작점 | `np.ones_like` | `Variable(np.ones_like)` |
| backward 내부 | `.data` 꺼내 ndarray 연산 | Variable 그대로 연산 |
| 역전파 API | `fill_grad(y)` | `fill_grad(y, create_graph=True)` (옵션) |
| grad 값 접근 | `x.grad` | `x.grad.data` (한 겹 더 들어감) |

참고: dezero는 `backward(create_graph=True)` 시그니처로 가지만, rezero는
`fill_grad` 전역 함수(항목 014 — 관심사 분리)를 유지할지 어떻게 진화할지가
step32의 설계 결정 사항. 정답지 `dezero/core_simple.py`와 `rezero/v1/core.py`를
나란히 보며 정할 것.

→ **step33 수확 예고**: 뉴턴 갱신 `x ← x - f'/f''`에서 f''를 `gx.backward()`로
자동 계산 — step29의 gx2 손유도가 완전히 사라지는 순간.
